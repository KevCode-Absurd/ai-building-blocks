

BullMQ-based job queue with Redis persistence, agent routing, lifecycle hooks, error classification, dead-letter queue, orphan recovery, and the worker bootstrap.What this system doesThis is a job queue system using BullMQ and Redis to handle asynchronous tasks like agent execution, messaging, and content generation in a scalable and reliable way.Core setup flow- Install dependenciesInstall bullmq and ioredis. - Provision RedisUse any managed provider like Render, Upstash, or Railway. Store the connection string in REDIS_URL. Most providers require TLS, so the URL will start with rediss://. - Configure environment variablesYou need Redis for the queue, Supabase for persistence, and a daily budget variable for agents. - Create the queueInitialize a BullMQ queue connected to Redis. This is where jobs get added. - Create the workerThe worker processes jobs from the queue. Key settings include concurrency (how many jobs run in parallel) and stalled interval (how long before a job is considered stuck). - Enqueue jobsAdd jobs to the queue with retry logic and exponential backoff. - Deploy the workerUse a background worker service (Render is recommended). Enable auto-deploy from your main branch and make sure your region matches Redis and Postgres to avoid latency.System architectureSupabase acts as the source of truth for job state.Redis (via BullMQ) handles job execution.The worker is responsible for processing jobs.The queue acts as a buffer between incoming tasks and execution.Reliability systemsThere are three critical systems that prevent failures in production:First, recovery logic. On startup, the worker re-adds jobs from Supabase that may have been lost due to crashes or Redis restarts.Second, retries with backoff. Temporary failures do not kill jobs permanently.Third, monitoring. This includes heartbeat tracking, queue depth alerts, and failed job notifications.Common failure casesJobs stuck in “queued” usually means Redis lost the job. The fix is to re-enqueue from Supabase.Worker restarts with no clear error are typically memory issues caused by high concurrency. Lower concurrency or upgrade the instance.Redis connection errors like ECONNRESET are usually caused by missing TLS config or incorrect retry settings. Set maxRetriesPerRequest to null and use rediss://.Duplicate job execution often comes from slow Slack acknowledgments. Always acknowledge events immediately before sending work to the queue.Jobs running more than once are caused by a stalled interval that is too short. Increase it for long-running jobs.A growing dead-letter queue indicates a permanent failure, such as a bad migration or missing environment variable. Fix the root issue before replaying jobs.If all jobs fail immediately due to budget errors, your budget environment variable is missing or too low.If jobs complete but no output is sent, the response function may not have been called, or there may be an issue with Slack integration or filtering.If the queue slows down due to internal jobs like heartbeats, prioritize user-facing jobs and reduce heartbeat frequency.If Redis runs out of memory, it is usually because completed and failed jobs are not being cleaned up. Configure automatic removal policies.Debugging checklistCheck queue status (waiting, active, failed).Check job status in Supabase.Review worker logs for errors.Inspect agent activity logs for the specific job.Look for common issues like Redis errors, budget limits, or stalled jobs.Bottom lineThis system is the execution engine of your agent infrastructure.If configured correctly, it scales reliably, handles failures, and supports heavy workloads like AI and video processing.If configured poorly, it leads to lost jobs, duplicated costs, and broken user experiences.
