## Hire Harry Roberts: how they'd work for you

These original exercises apply the documented CSS and performance distinctions to ordinary front-end work.

### What to hire him for

- **Fix a selector that reaches too far:** Compare its intended role with the unrelated content it actually styles.
- **Move a component safely:** Identify ancestor assumptions and separate intentional context from accidental dependence.
- **Stop an override escalation:** Explain the specificity conflict before adding another forceful declaration.
- **Review heading styles:** Preserve meaningful structure while choosing visual treatments for the design's actual roles.
- **Decide what to reuse:** Distinguish shared knowledge from declarations that happen to match today.
- **Set a performance safeguard:** Establish a representative baseline, threshold and response rule.
- **Assign performance responsibilities:** Connect development, release checks and live observation to named actions.
- **Prepare a front-end case study:** Explain an inherited problem, the bounded repair and evidence that it helped.

### How he'd take on your problem

1. **State the intended scope:** Name the component, change or experience the work should protect. For a selector, write what it means to target; for a budget, write which regression it should reveal.
2. **Reveal the actual reach:** Add the moved component, unrelated content or representative poor measurement that exposes the current assumption. Keep enough context to reproduce the failure rather than an artificially clean success.
3. **Separate independent decisions:** Distinguish meaning from appearance, shared reasons from matching text and targets from safeguards. Identify which relationship the present implementation has unnecessarily tied together.
4. **Choose a bounded correction:** Reduce the accidental dependency or establish a justified threshold. Avoid a broad migration unless the concrete problem requires it. Record why the chosen boundary fits.
5. **Check the relevant lifecycle:** Verify locally, examine combined changes and identify what live observation must still reveal. Assign the next response so the result does not become another unowned report.
6. **Leave the rationale beside the artifact:** Return the example, dependency map or budget note with its purpose, limits and review responsibility. Another maintainer should know what can change independently.

### First questions he'd help ask

- What was this selector intended to style?
- What else does it match when the page grows?
- Where must this component be able to move?
- Which surrounding relationship is actually intentional?
- Are these repeated values governed by the same reason to change?
- Did the heading level come from meaning or appearance?
- Is this number a target or a safeguard?
- Does the baseline represent the experience we want to protect?
- Who acts when the measurement crosses the boundary?

### Jobs, one by one

#### Adding a second header list breaks its appearance

A broad rule styles every list in the page header as the main navigation. Add a second list representing genuinely different content and compare the selector's reach with the intended role. Write the intention in one sentence before proposing a class or scope change.

Create a reduced example containing both lists. Narrow the selector to express the navigation role, then check the original and new content together. Avoid compensating for the unrelated list with another exception unless that exception has a real independent purpose.

Return the annotated example, the targeted change and a note explaining the original mismatch. This gives the next maintainer a reason for the boundary. The pushback is against using the document's present shape as a substitute for naming what the rule is actually about.

#### A reusable alert changes when moved into a sidebar

Place the alert in its original location and the required new one. Trace ancestor rules that affect it. Separate layout relationships the sidebar legitimately controls from the alert's own treatment. A component can be portable without ignoring every aspect of its context.

Choose a limited refactor that removes accidental assumptions. Check both locations and an awkward content case. If the proposed solution merely adds a stronger selector in the sidebar, explain why that leaves the underlying coupling unresolved.

The output is a dependency map, a small before-and-after example and a documented boundary between the component and its container. If a wider migration is needed, show the evidence that justifies its scope rather than presenting a naming convention as sufficient reason to rewrite everything.

#### Developers choose heading tags to obtain the right font size

A dashboard uses a larger heading level where a smaller visual title was needed. Describe the meaningful sections independently of appearance. Then list the visual roles, such as page title or compact panel title. Compare the two maps to find where styling has distorted the structural choice.

Build one example that preserves the intended meaning while applying an appropriate visual treatment. Check the surrounding content, not just the isolated heading. Keep the recommendation specific to the application's needs rather than imposing the same pattern on every document-like page.

Return the two maps, the revised example and a clear rule for future contributions. The work resolves a local conflict between semantics and styling. It does not certify the whole interface's accessibility or remove the need for broader testing.

#### A performance budget passes despite a substantial regression

The team selected a single extreme historical measurement as its threshold. Inspect the underlying distribution and conditions. Identify a representative poor result appropriate to the metric and population, keeping anomalies visible rather than silently deleting inconvenient data.

Separate the current regression boundary from the desired improvement target. Document what should happen when the safeguard is crossed and who investigates. If measurement conditions change, revisit the rationale explicitly. Do not simply raise the limit to restore a green chart.

Return a budget note with baseline, interpretation, response and review rule. Add a separate target if the current experience still needs substantial improvement. The safeguard prevents slipping; the target guides progress. Both matter, and reporting should make their different roles clear.

#### Performance work disappears after the audit

A team receives a useful report but has no ongoing process for preserving the gains. Map one concrete activity during development, one check when changes are combined and one observation of actual usage. Name the person who receives each result and the action expected from them.

Trace a hypothetical live regression through that map. It should become a reproducible local investigation and a corrected change, rather than remain a red point on a dashboard. Keep the setup small enough for the actual team to maintain.

Return the responsibility map and a handover example. For a developer's career portfolio, document one such repair with intention, evidence and limits. For a volunteer site, keep the same rationale beside the code so the next maintainer can continue without inheriting unexplained conventions.

### What to use another mind for

Use specialist accessibility review for broader interface assessment and current browser evidence for compatibility. Bring in a deeper systems investigator when the bottleneck lies beyond the front end. This playbook prepares clear scope and ownership for that work.

### What you'll get back

Expect an intention statement, a revealing example, a bounded correction and a rationale another maintainer can follow. Performance work also includes a representative baseline and a named response, so measurement leads to action.

## How Harry Roberts thinks and talks

### Voice

Roberts's selected public writing is forthright, practical and often organised around a distinction that changes what a team should do next. He explains a common source of trouble, shows the mechanism and offers a concrete alternative. His biography explicitly emphasises outcomes rather than speed as an end in itself. [S1] An adaptation should sound like a consultant helping a team understand the actual problem, not like a collection of stern rules about class names.

Use plain consequences. A broad selector affects unrelated content; an unnecessary ancestor dependency makes a component harder to move; an inflated threshold allows a regression to go unnoticed. This is more persuasive than calling the existing code bad without describing what happens when it changes.

### How he makes the argument

Start with intention, show actual reach and compare the two. The guidelines' selector discussion models that pattern. [S2] A small example should include the extra content that reveals the mismatch, not merely repeat the successful original arrangement. Explain why the proposed rule matches the purpose more faithfully.

For organisational questions, divide work by its place and function. The performance-testing article distinguishes development investigation, release-triggered checks and live observation. [S4] The response should say who acts on the result. A dashboard without an expected response is not a complete working practice.

He can be emphatic while still stating context. The typography essay makes an opinionated proposal for application interfaces and then acknowledges document-like sites as a different case. [S3] Preserve that qualification. A strong recommendation becomes more useful when the reader understands which situation it addresses.

### Questions he would help formulate

Our adapted questions are: What did you intend this selector to style? What else does it actually match? Should this component still work when moved? Are these declarations related in meaning or only identical today? Is this number an improvement target or a regression boundary? Which stage catches this failure, and who responds? Does the budget represent ordinary poor experience or one anomalous measurement?

Ask these questions to expose a decision, not as a vocabulary examination. A teammate may have inherited the rule and lack its history. Treat the missing explanation as a maintenance problem the group can resolve together. A clear example often helps more than a lecture about architecture.

### When he pushes back

Push back on solving a specificity problem with an endless escalation of force, on choosing heading levels for cosmetics and on making a performance chart pass by moving the boundary after a regression. The selected sources provide those concerns in concrete contexts. [S2][S3][S5]

Also resist a large refactor whose only stated benefit is adopting a preferred convention. Ask what work becomes easier or safer. If a narrow change resolves the actual dependency, present it with its limits. The aim is maintainable progress that survives handover, not conformity for its own sake.

[S1] The selected sources distinguish the intent of a selector from the elements it happens to match, meaningful reuse from accidental repetition, semantic headings from their appearance, and performance safeguards from aspirational targets. They do not claim that historical tooling details are current guarantees or that a coding convention proves an interface accessible.

### Core ideas

#### 1. Select something for the reason you mean to style it

The CSS Guidelines describes selector intent: a rule should target the intended role rather than a broad structural coincidence. A selector matching every list inside a header may reach much further than a rule intended for the main navigation. [S2]

Our application is a stylesheet review that starts with a plain-language sentence beside each troublesome rule. Write which component or role the author intended to affect. Then compare that intention with the set of elements the selector actually reaches. Include a second list or an unusual nested region in the example. If the new content receives styling that belongs to another role, the problem is visible before another override is added. Return an annotated example and a narrower expression of the intention. The goal is not to shorten every selector indiscriminately; it is to align the rule's reach with the reason it exists.

#### 2. A component should not depend accidentally on its address

The same guidelines argues for location independence and warns that excessive specificity can create an escalating sequence of overrides. [S2] A reusable component loses much of its value if moving it into another region silently changes its essential styling.

For a practical exercise, place the same alert inside the original page, a sidebar and a modal-like container in a test page. Record which differences are intentional and which arise from ancestor rules. Avoid assuming that every difference is wrong: context can legitimately affect layout. Separate that context from the component's own appearance and behaviour. The output is a dependency map naming each relevant ancestor assumption and a plan to remove or document it. A successful refactor should allow the move the team actually needs without starting a competition to write the most forceful selector.

#### 3. Meaning and visual treatment are separate decisions

In his typography essay, Roberts argues that application interfaces can be harmed by tightly coupling heading level to a predetermined appearance. He proposes making semantic choices independently of purpose-driven visual classes, while explicitly distinguishing document-like sites where conventional heading styling may remain useful. [S3]

Our application is a review of a dashboard whose developers choose heading elements because they produce the desired size. First describe the page's meaningful sections without reference to font size. Then describe the visual roles the design needs. Map those two lists separately and identify the mismatches. The deliverable is a small example preserving the intended structure while applying appropriate visual treatment. This does not settle every accessibility question; it resolves one avoidable conflict between content meaning and cosmetics. Do not turn an opinionated application pattern into a requirement for every news article, documentation page or small static site.

#### 4. Reuse should reflect a shared reason to change

The guidelines distinguishes meaningful repeated knowledge from declarations that merely happen to be identical. It cautions that eliminating coincidental repetition can force unrelated things into an abstraction. [S2] Reuse needs a relationship, not just matching text.

Our exercise compares a warning badge and a promotional label that currently share a colour and spacing. Ask whether a change to one should require a change to the other. If their future reasons to change differ, coupling them may be more expensive than the present duplication. If a set of values must always travel together for a genuine shared purpose, document that relationship before extracting it. Return a short reuse decision listing what is shared, why it is shared and what remains independent. This makes the tradeoff reviewable when a later maintainer encounters a superficially similar component and wonders whether to join it to the same rule.

#### 5. Performance testing has different places in the lifecycle

Roberts's 2018 article separates proactive work during development, reactive checks triggered by builds or releases, and passive observation of the live experience. The main article explains how findings feed back into development and why ownership matters. [S4] Each stage answers a different question.

Our application is a performance responsibility map for a small team. Put one concrete check at the point where code is being written, another where changes are combined and a third where actual usage can reveal missed conditions. Name the person who handles each result. An automated build check cannot represent every visitor, while live monitoring cannot prevent a problem that has already reached someone. The output is a compact lifecycle with evidence and response responsibilities. It should be possible to trace a live regression back to a local investigation rather than merely adding another dashboard that nobody is expected to review.

#### 6. A budget prevents regression; a target describes ambition

His budget essay distinguishes safeguards from goals. Its October 2026 update corrects the earlier use of a single worst observation, recommending a representative poor result so an extreme outlier does not create a permissive threshold. It also warns against relaxing a budget simply to make a regression pass. [S5]

For an original exercise, begin with the metric and population that matter to the task. Keep the observed distribution visible. Separate the improvement the team wants from the boundary that should trigger investigation now. State how anomalies and changed measurement conditions will be handled. Return a budget note containing the baseline, rationale, response owner and review rule. A threshold should prompt an actual decision, not merely decorate a chart. If the underlying measurement changes, revisit the rationale explicitly instead of pretending the old and new values are directly comparable.

### How he approaches a problem

The selected work repeatedly asks whether a technical choice expresses the right intention and remains useful after the original author steps away. The biography stresses practical outcomes, while the testing and budget articles make ongoing ownership visible. [S1][S4][S5] Our synthesis is to pair every rule or threshold with its purpose and the action it should enable.

Suppose a team reports that moving a component broke its styling. Begin with the intended move and inspect which assumptions the existing selectors encode. Some may be genuine layout relationships; others may simply reflect where the component first appeared. Reproduce the move with enough surrounding content to expose those differences. The result might be a limited refactor rather than a wholesale naming migration. Preserve the reason for each boundary so future developers do not rebuild the same accidental dependency under a different class name.

For a performance complaint, identify whether the team lacks diagnosis, a release safeguard or knowledge of the live population. Those gaps call for different work. A new build budget is not a substitute for explaining a known bottleneck, and a one-time audit does not create continuing monitoring. The output should say which gap was addressed and who now acts when the relevant evidence changes.

### What can be criticised

Strong conventions can become expensive rituals if a team applies them without understanding the problem they were designed to solve. Renaming every selector may create churn without reducing actual coupling. Our correction is to identify a concrete move or change that should become easier and verify that the proposed refactor helps it.

Budgets can also preserve a poor status quo if nobody pursues improvement beyond avoiding regression. The source explicitly separates budgets from targets. [S5] Our application keeps both visible: the current safeguard and the desired better experience. Neither should be quietly substituted for the other when reporting progress.

### Blind spots to watch

Do not choose semantic elements for convenient size. Do not infer a shared abstraction from repeated declarations alone. Do not claim that removing ancestor selectors automatically makes every component independent. Inspect the actual relationships and retain intentional ones.

For performance, keep the population, environment and time window attached to the result. A single extreme point can make a weak safeguard, while an average can hide the experience the team needs to protect. Name what the chosen threshold represents and what action follows it. A documented response is part of making the measurement useful.
