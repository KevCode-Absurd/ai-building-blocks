Generic AI products remain useful foundations and possible distribution channels. PRODUCT REQUIREMENTS

As of 17 October 2026 | Version 2026-10-17-current-five-stream-plan

THE COMPLETE CUSTOMER LADDER

Prompt: one task, explicit inputs, approved company context and an example result.

Skill: reusable instructions with optional scripts, references, input checks, failure cases and output tests. It can work alone.

Workflow: an ordered set of selected skills, tool calls, calculations and human checkpoints. Its configuration records which modules are enabled and the evidence each one needs.

Routine: the same workflow with an approved schedule or trigger, a durable runner, failure alerts and an owner. A downloadable instruction file alone is not a scheduler.

Agent or worker: a bounded responsibility with approved skills, tools, saved state, budgets and escalation rules. Multiple roles may cooperate only where evaluation shows a benefit.

Application: a customer interface plus database, access controls, agents or workflows, logs, deployment and maintenance. A full application is a separate engineering scope, not automatically included in a library subscription.

MINIMUM PRODUCT EXPERIENCE

Discover by exact task, function, industry, output and host. A task page shows a complete labelled sample, required inputs, compatible tools, likely review effort, limits and last evaluation date. Industry-specific examples should be easy to find without forcing every customer through the same template.

Preview the output, choose modules, select a data route and confirm the payer. For example, a user can request only Meta data, only three analyses, a chosen database destination and an audit-only report. The configurator validates prerequisites and creates a versioned configuration; it should not blindly generate arbitrary executable code.

Provide a manual download pack as well as supported integrations. The pack contains the method, input template, selected permitted references, output contract and setup instructions. Preserve a useful fallback when an account cannot use a connector or a native host tool is unavailable.

Save private company facts, accepted outputs, rejected references and settings under the correct organisation and brand. Shared methods and public references remain separate from private customer evidence. Agencies need client boundaries, member roles and approval ownership.

Explain the next useful step after a result: repair missing data, research a creative gap, prepare a new brief, create an asset, schedule a repeat review or stop. A suggested next task does not itself authorize a paid run or write.

PROPOSED FIRST RELEASES

First prove a brand-aware audit and a reference-backed static-ad task. Candidate audit modules are data readiness, basic efficiency totals, creative diversity, new-versus-established spend mix and optional fatigue analysis. Every module needs an exact definition and an unavailable state when evidence is missing.

Candidate launch pages are a brand or landing-page audit, a scoped Meta ad audit and a BFCM static-ad brief or creation workflow. Creative-fatigue review is a separate module with daily-history requirements. These are proposed launch choices, not completed products or a commitment to launch every module together.

Acceptance for a first release means an approved test brand, at least one held-out brand, deliberate failure cases, usable final artifacts and measured human effort. Thresholds and sample sizes must be set before judging the candidate. A small demo or model self-score cannot establish production readiness.

LIBRARY AND REFERENCE BOARDS

Use boards for static ads, videos, editorials and other relevant outputs. Tag assets by industry, product type, audience, message, offer, format, visual treatment, date and source. Store ownership or licence evidence, permitted uses, expiry and any restrictions on downloads, model use or redistribution.

Customers can browse and pick references or ask the platform to rank relevant options against their approved brand profile and task. Return reference IDs, roles and selection rationale. A layout reference is not authority to copy a competitor's claim, logo or protected product image.

The selection packet must make actual permitted media available to the execution route. A board URL or preview thumbnail alone is not proof that a model inspected the asset. Support manual attachment when native media delivery fails.

Foreplay and similar libraries are potential source tools, not assumed rights to mirror or resell every asset. Verify terms, export/API access and rights for each intended route. Keep private client boards private. A no-match result is better than an irrelevant or unauthorised reference.

WHY CHOOSE US AND KEEP PAYING

Differentiate on a narrow task, demonstrated output, company-specific configuration, tested methods and accountable implementation. Measure whether customers actually finish useful work faster with less correction than with their existing setup.

Paid renewal supplies maintained releases, fresh permitted references, compatibility updates, saved team standards and defined support. Show release notes and evaluation evidence. Keep accepted work pinned to its exact method and reference versions, with a deliberate upgrade path.

Scale by reusing methods, schemas, calculations, connectors, examples and training. Keep standard setup bounded, charge for unique engineering and train delivery partners. Add outside builders only after there is a review process, a licence model, maintainer responsibility, incident handling and evidence of buyer demand.


SYSTEM AND INTEGRATION PLAN

PROPOSED ARCHITECTURE

Separate the reusable library from customer execution. The library service manages catalogue search, task releases, reference metadata, entitlements and permitted reference packets. A customer workspace holds its private company profile, source snapshots, configuration and outputs according to the chosen deployment.

The website, customer API and MCP interface call the same domain services. That prevents different reference rules, permissions or charging depending on the surface. Native-host adapters translate the canonical task and media packet into the host's supported format. A separately deployed runner is needed for durable jobs when a native host cannot supply the required persistence or scheduling.

Keep calculation and validation steps deterministic where possible. Use models for interpretation, selection, critique and drafting where their contribution can be measured. A workflow diagram with many agent names is not evidence that the system needs that many independent agents.

DATA OBJECTS AND CONTRACTS

Organisation and brand: ownership, members, roles, approved facts, products, claims evidence, style, source accounts and default definitions.

Task release: immutable identifier and version, goal, input schema, required permissions, compatible host profile, scripts, output schema, tests, known limits and maintainer.

Workflow configuration: selected release IDs, module options, dependency order, source and date window, output destination, permitted tools, budgets, review policy and optional recurrence.

Reference asset and packet: source ID, board ID, revision, allowed uses, access expiry, media type, selected role, brand/task fit and the representation actually delivered to the host.

Run and step records: task and parent IDs, actor, input/configuration hashes, snapshots, status, attempts, cost receipts, evidence references, outputs, approval and errors.

Finding: stable ID, observed fact, calculation or evidence, confidence, missing inputs, impact basis and proposed next action. An action proposal remains distinct from approval to execute it.

Handoff: accepted finding IDs, private context revision, task and reference versions, already-satisfied inputs, missing prerequisites, destination, reviewer, budget and permitted tools. Never use a model-supplied organisation ID as the sole access check.

PUSH AND PULL ROUTES

Pull: a customer asks their assistant for a task; the installed method calls our authorised catalogue/reference tools or API. The service authenticates the user, enforces organisation/brand scope and entitlement, and returns a bounded versioned packet. The host uses its own available tools or an explicitly funded external route to finish the work.

Push: a customer opts into a routine or notification. A scheduled job prepares a new result or digest and writes to the approved customer destination or notifies the owner. This needs an actual runner, destination credentials, failure recovery and a saved policy. Our website cannot silently inject files into an unrelated private chat.

Download: the customer exports a permitted context/method/reference pack and attaches it manually. This is a first-class route for trial, portability and unsupported integrations. Show what goes stale, what is licensed and what requires a new retrieval.

Meter one underlying operation once across website, MCP and API. Use idempotency keys for retry-safe paid steps. Reserve and reconcile platform-funded usage. When an outcome is unknown after a timeout, check the existing operation before submitting another charge or write.

GATEWAY AND CONNECTOR CHOICES

A single branded gateway is a possible access layer, not a reason to rebuild every third-party connector. It should own our task/reference logic, identity boundaries, entitlement, logging and consistent contracts.

Composio is a candidate for delegated connections to supported business tools. The earlier spoken term Composer is ambiguous; do not assume it names a selected provider. Compare vendors and direct connectors on exact tools/fields, OAuth scopes, tenant separation, data paths, retries, audit logs, costs, private deployment and exit/export options.

Start with the smallest supported set and read-only data access. Keep provider credentials server-side or in the customer's approved secret store; never place them in prompts, downloadable skills or public artifacts. A connector vendor does not replace our data-quality checks, media rights, evaluations or customer authorisation.

DEPLOYMENT AND DATA BOUNDARIES

Offer manual/native use first, then customer-cloud or managed deployment when justified. A later on-prem route needs private-network access, secret handling, backups, monitoring, updates, licence checks and an owner. The proposed application layer includes interface, database, access rules, execution history, cost controls and recovery. BRAND AUDIT WORKER WALKTHROUGH

The worked audit is a scoped Meta creative-programme review, not an unlimited audit of every business function. Confirm brand/account, exact closed date window, timezone, currency, conversion event, attribution, source grain and selected checks. Start with a customer export or a separately authorised read connection.

Freeze one input manifest and data snapshot. Validate required columns, IDs, duplicates, joins, date coverage, currencies and source totals. Block dependent analyses when evidence fails and report partial availability clearly. Reconcile calculations in scripts rather than asking a model to estimate totals.

Run compatible independent checks on that same snapshot: efficiency numbers, mapped entity coverage, semantic creative diversity, claims review, new-versus-established spend mix and optional fatigue analysis. Asset-based checks need actual accessible creative. Fatigue requires comparable daily history and sufficient volume; window totals alone do not establish it.

Resolve the customer's meaning of entity ID. Distinct ad IDs do not prove distinct messages. Spend is observed delivery; budget is a setting that may sit above the ad level or change. Do not manufacture budget allocation from spend or infer launch dates from an incomplete export.

Collect typed findings with evidence, calculations, uncertainty and missing inputs. Reconcile conflicting modules. A presentation step uses those accepted findings to create the PDF; it cannot invent new numbers or conclusions. Render and inspect the actual final PDF, charts and tables.

Deliver the PDF, a machine-readable findings file, the scope/definition record and a small set of supported next actions. Report acceptance, the next task and external publication are separate decisions. Failed or unavailable branches remain visible.

TYPED HANDOFF TO THE NEXT WORKER

An accepted missing-data finding can lead to a mapping/repair proposal and revalidation. An accepted creative gap can lead to research, reference selection and a replacement brief. A fatigue hypothesis can lead to a controlled test plan after alternative explanations are reviewed.

The handoff carries finding IDs, evidence and snapshot references, brand-context revision, target task release, known inputs, missing prerequisites, expected artifact, destination, budget, reviewer and allowed tools. The next worker validates these before use. It does not receive unrestricted raw data or broader permissions merely because another agent suggested the task.

Offer alternatives including stopping or using a human. A saved routine may follow its pre-approved policy; a new scope, consequential write or newly paid operation needs the appropriate user decision. Record whether the action was actually completed and whether the original issue was resolved.

EVALUATION AND RELEASE PROCESS

Review source/licence, scripts, dependencies and requested permissions. Test normal, missing-data, wrong-brand, stale-source, inaccessible-media and hostile-input cases. Treat retrieved pages, ads and reference text as evidence, not instructions to change tool permissions or reveal secrets.

Use a development brand, held-out cases and deliberately failing fixtures. Record output acceptance, evidence correctness, calculations, asset fidelity, support minutes, latency and cost. Compare candidates against the current release under matched conditions; do not rely solely on a model grading itself.

Release immutable versions with a maintainer, test date, supported host/tool profile, known limits and rollback path. A model, schema, adapter or method change triggers affected downstream tests through the final artifact. Pin accepted campaigns to prior versions until an upgrade is reviewed.

Test interruption and recovery: expired references, connector failure, quota exhaustion, partial report creation, rejected access and unknown paid-operation outcomes. Bound retries, concurrent work and total run cost. Separate security risk reduction from an absolute safety guarantee.
