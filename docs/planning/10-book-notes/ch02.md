# Chapter 2: Understanding Foundation Models: notes and how we use it

> Our mapping of one chapter of Chip Huyen's *AI Engineering* (O'Reilly, 2025) onto our stack, written 2026-10-18.
> The reader's section-by-section summary of the book (section 2) is left out on purpose, so sections run 1, 3, 4…; these notes keep only how the ideas apply to us.
> Book section names are given so the original can be found. The master is `../10_AI_ENGINEERING_FRAMEWORK.md`; where they differ, it wins.

## 1. The chapter in brief

The chapter explains the design choices behind a foundation model that affect the people who build on it. There are four: what data it was trained on, its architecture and size, how it was post-trained (supervised finetuning, then preference finetuning), and how it picks each output token (sampling). Huyen's main claim is that sampling is the most underrated of these. It explains why models give different answers to the same question and why they make things up. It is also the cheapest lever we have: run more than one sample, choose with a verifier, or constrain the output format.

Why it matters to us: we never train a model. We call four labs through their APIs and publish listings that claim to be "tested". This chapter says what "tested" has to mean for a probabilistic system:
- quality is a rate across repeated samples, not one good run;
- format has to be enforced in code, not hoped for;
- hallucination is built into how these models work, so our "zero wrong prices / zero invented claims" rule must be enforced by checks and by schemas that allow "not found", never by trust;
- each lab's training data and post-training make it behave differently, which is the reason to test on all four.

**One important update since the book was written.** On current Claude models (Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Opus 4.7/4.8), `temperature`, `top_p` and `top_k` are removed, or rejected if set to anything but the default. Effort is the only control. OpenAI's reasoning models behave the same way, as far as I know (to verify). So "set temperature 0 for consistency" is mostly no longer available on the models we will recommend. That makes the chapter's other answer, **sample several times and verify**, the main one for us.

## 3. How we apply it: by building-block level

### The two policies this chapter gives us (used across all levels)

**A. Sampling policy: a new `sampling` block in `item.yaml`, translated per model by `_models.yaml`**

| Item kind (examples) | `sampling.mode` | Where the model accepts temperature | Where it doesn't (current Claude, OpenAI reasoning models) | Effort / reasoning |
|---|---|---|---|---|
| Extract / classify / tag / map columns / read prices (`website-claims-extractor`, `product-photo-tagger`, review tagger) | `low_variance` | T = 0–0.2 | send nothing; log `sampling_applied: provider_default` | low |
| Judge verdicts (`grade`) | `low_variance` | T = 0 | send nothing | low–medium |
| Rules-based short writing with variants (hooks, headlines, ad copy) | `creative` | T ≈ 0.8–1.0 (1.0 for DeepSeek and Gemini defaults) | send nothing; get diversity by asking for N distinct variants in one call | medium |
| Long reasoning (strategy brief, audit, script) | `provider_default` | default | default | high |
| Agent / workflow planning steps (C4 planner) | `provider_default` | default | default | high |
| Numbers (mini tools, offer maths) | n/a: **computed in code, never by the model** | | | |

Rules:
- Never set top-k.
- Never set both temperature and top-p.
- Seeds: use them where a lab supports them, and log them, but never rely on them for consistency.
- `run-test` records what was actually applied for every call.

**B. Structured-output policy: a new `output` block in `item.yaml`**
- **Required (`output.structured: true`)** whenever code reads the output:
  - `grade` code checks on fields (character limits, claim IDs, prices);
  - the next step in a workflow;
  - `build-graph`;
  - tool calls;
  - classification, extraction and judge verdicts.
- Copy items are included too: ad copy returns `{variants: [{hook, body, cta, claim_ids[]}]}` so character limits and claims are checkable. The site renders it as plain text.
- **Not required:** human-only prose such as a guide or an explanation.
- **Enforcement stack in the factory, in this order:**
  1. the provider's native schema mode (Claude `output_config.format` / `strict` tools, OpenAI strict JSON schema, Gemini response schema; DeepSeek JSON mode with a schema in the prompt);
  2. our defensive parser (§2, Post-processing), with repairs logged;
  3. schema validation in code (zod) plus the null/evidence rules from Hallucination §2;
  4. on failure, retry at most 2 times, sending back a one-line error;
  5. after that, fail the run.
- **Never** use a model to repair format.
- **Record** `format_valid_first_try` and `format_valid_after_retry` per model. Retries count toward cost per finished outcome (`05` §13).
- **No-code downloads** (ChatGPT, Claude.ai) can't use schema modes. Their exports include the schema as an example block plus a "check your output" checklist. The listing page states that the format was tested through the API only.

### Platform (factory, site, intake, data)

**`run-test` defaults (concrete):**
- `samples_per_input` (k):
  - **3 by default**;
  - **5** for `low_variance` items (extract, classify, judge) on the recommended and budget models;
  - **1** for the class that is clearly worse after the first pass, to save money.
- Golden inputs: 5 (prompts and skills), per `06` §10. Add **2 perturbed variants** of one input: a casing/wording change and a reordered or paraphrased brief. Together with the existing position test, this covers both kinds of inconsistency.
- Per model, record:
  - pass rate across all samples;
  - **worst-of-k** per input;
  - **field agreement** (structured outputs: share of samples with identical values for each key field);
  - **judge-category agreement** (text items);
  - `format_valid_first_try`;
  - refusals;
  - stop reasons;
  - provider-reported tokens;
  - `sampling_applied`.
- **Gate change:** costliest mistake = 0 across **every sample**, not on average. A single wrong price in 45 runs fails the item.
- Page wording uses counts: "0 wrong prices in 45 runs; prices are also checked by code on every run".
- Budget check (an assumption to replace with measured numbers): 5 inputs × 3 models × k=3 = 45 generations, plus 45 judge calls. At about $0.002 (cheap), $0.02 (mid) and $0.08 (top) per call, plus about $0.01 per mid-class judge call, that's about $2 per item round, well inside the $25 round cap. k=5 on two models adds about $0.5.

**`grade` defaults:**
- Judge from another lab, at **mid class**, in `low_variance` mode, with a structured verdict schema: `{criterion_id, category: fully|partly|not, evidence, reason}`.
- **Judge self-consistency:** for each new rubric version, re-run the judge 3 times on 10 outputs. Require ≥90% category agreement with itself, and ≥80% with Kevin's hand grades on the same 10, before the rubric counts. Version the judge prompt (`05` §16).
- Prefer **pairwise blind A-vs-B** for "did this change help" (step 8 in FINAL_PLAN §12, "fix until it beats the original"). The book's reward-model section shows comparisons are more reliable than absolute scores.

**`_models.yaml`:**
- Add a per-model `sampling_support` entry (temperature yes/no and range, top-p, seed, JSON schema mode, logprobs) and a per-mode translation.
- Fill it from each lab's current docs in build week. For Claude it is already known: no sampling parameters on current models, effort only; structured outputs through `output_config.format`; strict tools; no prefill.

**`check-item`:**
- Fail if an item has `output.structured: true` without a schema.
- Fail if a factual schema field isn't nullable or lacks evidence.
- Fail if `max_tokens` isn't set from measurement.
- Fail if `languages_tested` is missing.

**Intake engine (`08`):**
- The chapter adds one reason to the "content is data" rule: content written to steer models.
- Idea cards from non-English sources need a note that the summary passed through translation (information loss).

**Site:**
- Each listing page shows a **Consistency** line (passes/samples, field agreement) next to quality and cost.
- A Learn lesson explains why it isn't 100% (§6).

## 4. What it changes in what we already wrote

**Agreements (the book confirms):**
- `05` §14, "changing the model: almost never": post-training is expensive and specialised, and every structured-output need is met by provider schema modes. Confirmed.
- `05` §3, maker plus separate checker: best-of-N with a reward model or verifier is industry practice, and verifiers can be worth a 30x model-size jump. Confirmed and strengthened.
- `05` §16, categories rather than 1–10, and pairwise checks: pointwise scores are noisy and comparisons are more reliable. Confirmed.
- `06` §10, re-testing when a major model ships and testing one class below: newer small models overtake older large ones, and inverse scaling exists. Confirmed.
- The `FINAL_PLAN` §12 "recommended = cheapest within 5 points" rule: last-mile economics. Confirmed.
- Mini tools computing in code: confirmed by the probabilistic-nature section.

**Corrections:**
1. **`06` §10: "One repeat run per model checks consistency" is too little.** One repeat can't estimate a rate. Replace it with k=3 (5 for low-variance items), pass rate, worst-of-k and agreement (§3, Platform).
2. **"Tested ✓" can't mean "never fails".** Public wording becomes counts ("0 in 45"). The guarantee for prices and claims comes from code checks on every run, which is already the design, but the wording must not promise more.
3. **The `05` §22 `item.yaml` example has no output schema or sampling fields.** Add:

   ```yaml
   sampling:
     mode: low_variance        # low_variance | creative | provider_default
     effort: low
     samples_per_input: 5      # used by run-test
     self_consistency: 0       # >0 = majority vote in production runs
   output:
     structured: true
     schema: schema/output.json   # factual fields nullable + evidence
     max_tokens: 1200             # p95 measured x 1.5
     max_retries: 2
   languages_tested: [en]
   ```

4. **`06` §3.1 says `run-test` runs "via the router".** That conflicts with the decided "no router service". It should call the four labs' APIs directly through a thin adapter that also does the sampling and schema translation. (`05` §10 still names OpenRouter/LiteLLM/Portkey as options for *users*; that part is fine.)
5. **Any temperature advice we planned to teach must be updated.** "Set temperature to 0 for consistency" doesn't apply to current Claude models and likely not to OpenAI reasoning models. Guides should teach "run it 3 times and compare" first, and temperature only for models that accept it.

**Gaps filled:**
- `05` §16 has no rule about **schemas that force invention**. Add it as a code check (nullable plus evidence).
- `05` §6 checks tool-call shape but says nothing about **truncation**. Add "stop reason = max_tokens → invalid".
- `05` §13 has no **output-token** lever or **retry cost** in "cost per finished outcome". Add both.
- `05` §17 has no **planted-content** case. Add it.
- `09` steps 2–3 (test set, evals) don't teach **repeat samples**. Add a lesson (§6).
- `09` step 9 (cheaper and faster) should add "a cheap model plus a code check often beats a top model alone", backed by the verifier evidence.
- FINAL_PLAN §12 step 6 (model test) gains the perturbation inputs. Step 7 (grade) gains judge self-consistency before a rubric version counts.

## 5. What we should not adopt (and why)

- **Training, SFT, RLHF/DPO or reward-model training of our own.** It costs from tens of thousands of dollars (about $130k for InstructGPT's demonstrations alone), needs labellers, and is pointless when provider schemas and prompts do the job. It stays at `09` step 10 as teaching only, by demand.
- **Constrained decoding libraries (guidance, outlines, llama.cpp grammars).** They need model weights or logits, and we are API only. Provider schema modes cover it.
- **Logprob-based selection or confidence.** Anthropic exposes none, others only partly. It isn't portable across our four labs. Use sample agreement.
- **Large best-of-N or self-consistency in recommended configurations** (beyond 3–5). Cost scales linearly and our caps are $2/run and $25/round. Gains past a few samples go to diminishing returns or verifier-fooling. Use k=3 for selection only where a code verifier exists.
- **Per-item temperature tuning as a routine factory step.** Current Claude models and probably OpenAI's reasoning models reject it, so it would be work for two of four labs at best. Use three coarse modes, translated per model.
- **YAML output to save tokens** (LinkedIn's choice). Provider schema modes are JSON. The token saving is small next to the reliability of native JSON schema.
- **Domain-specific or non-English model hunting.** Not our market at launch. General models from the four labs cover ecommerce and SaaS well.
- **Classifier heads or architecture changes.** These belong to self-hosted finetuning, which we don't do.
- **Hosted parallel "first valid wins" latency tricks.** We have no hosted runs until site v3. Revisit then.
- **Answer caching in our factory runs.** It would hide the variance we're trying to measure. It's fine only in the user's own app template, for generic outputs.

## 6. What we teach users (Learn / Make it yours)

**Beginner**
1. **"Why does AI give a different answer each time?"** The dice analogy: the model picks words by chance, weighted by likelihood. That's why one run proves little. Action: run your prompt 3 times and compare before you trust it. (Fits `09` step 1, check by eye.)
2. **"Why AI makes things up, and the one-line fix."** The model would rather guess than leave a blank. Give it permission to say NOT FOUND, ask for short answers, and ask it to quote where each fact came from.
3. **"English works best."** These models learned mostly from English. If you work in another language, test in it, and expect it to cost more (more tokens).

**Intermediate**
4. **"Make AI fill a form, not write an essay."** Ask for a fixed format (a table or JSON) with an example. Check that every field is present. Why: code, sheets and other tools can only use output in a fixed shape. (Links to `09` step 3 code checks.)
5. **"Test the same thing several times."** Upgrade the test set (`09` step 2): 10 inputs × 3 runs each, plus 2 slightly reworded inputs. Count passes. A prompt that passes 30/30 is different from one that passes 22/30.
6. **"Ask for five, keep the best."** Best-of-N for creative work: generate 5 hooks, score them against your checklist, keep the top 2. Each extra version costs about one more run.
7. **"Let a different AI do the grading."** Comparisons ("which of these two is better?") are more reliable than 1–10 scores, even for people (they agree only about 7 times in 10).

**Advanced**
8. **"Settings that matter, and the ones that don't any more."** Temperature, top-p and top-k explained in two lines each. Which of the four labs still accept them. Why "effort" or "reasoning" is the newer control. Never change both temperature and top-p.
9. **"Schema mode in each lab's API."** Turn on structured outputs (Claude, OpenAI, Gemini, DeepSeek JSON mode). Validate in code anyway, retry twice, and watch for cut-off output (the stop reason). Comes with our eval kit's script (`09` step 3).
10. **"A cheap model plus a checker beats a pricey model alone."** The verifier result in plain words, with our own model-test numbers as proof. (Fits `09` step 9.)

**Expert**
11. **"Majority vote for facts."** Extract a price or date 3 times and accept it only if all agree; otherwise ask a person. Plus the rule of three: zero failures in n runs means "under about 3/n", not "never".
12. **"What training changes, and what it doesn't."** Pre-training versus SFT versus preference tuning, in plain words, and why preference tuning can make a model more agreeable and sometimes more confidently wrong. Feeds `09` step 10's "when not to train".
