# Chapter 6: RAG and Agents: notes and how we use it

> Our mapping of one chapter of Chip Huyen's *AI Engineering* (O'Reilly, 2025) onto our stack, written 2026-10-18.
> The reader's section-by-section summary of the book (section 2) is left out on purpose, so sections run 1, 3, 4…; these notes keep only how the ideas apply to us.
> Book section names are given so the original can be found. The master is `../10_AI_ENGINEERING_FRAMEWORK.md`; where they differ, it wins.

## 1. The chapter in brief

Chapter 5 was about the instructions, which stay the same for every query. Chapter 6 is about the **context**, which changes with each query. It covers two ways to build it. **RAG** fetches the relevant slice of an outside store before the model writes. **Agents** let the model use tools to collect information and act. The chapter's main claim is that the retriever, not the generator, decides how good a RAG system is. Term-based search (BM25) is a strong, cheap baseline that is hard to beat. Embeddings help with meaning but blur exact strings like SKUs. Real systems mix both and then rerank. Agents are defined by their environment and their tools. They succeed or fail on tool inventory and planning, and their errors compound across steps (95% per step gives about 60% over 10 steps). That is the numeric case for our "workflow first, short leash" rule. The chapter ends on memory: internal knowledge, short-term context and long-term external storage, and how to manage what moves between them.

Why it matters to us: almost every listing is a context-construction problem (brand brain, digests, references, exports). Ladder steps 2 (connect), 4 (schedule) and 8 (act) are the tool-and-agent part of the book. The chapter gives us a way to decide, per listing, whether to **stuff the context, retrieve, digest, query, or use an agent**. Right now `05` says how to retrieve but not when.

## 3. How we apply it: by building-block level

### The decision we were missing: stuff, retrieve, digest, query, or agent
This is a new default for every listing, recorded as `context.mode` in item.yaml and checked by `check-item`. The thresholds are proposals to be adjusted after the first model tests.

| Mode | Use when | Our examples | How it runs on the user's side |
|---|---|---|---|
| **stuff** (default) | The material this job needs fits a per-listing budget (proposal: **≤ 30k tokens**, well under every tested model's window) and is mostly the same each run. Book basis: Anthropic's under-200k guidance in "RAG", plus the cost and lost-in-the-middle caveats. | Brain card (1–2k) + named brain sections + digest (≤ 3k) + 3 references + rules | Paste or Project instructions; cached prefix |
| **lookup by key** | The store is structured and small, and the item knows *which* entries it needs | Brain sections by name, offers where `current: true`, claim IDs, a SKU's record | Code or the skill reads named files and fields; **no similarity search** |
| **retrieve** | The material is large or growing, varies per query, and the question is a **point lookup** ("find what the book says about headlines", "which policy covers before/after photos") | A copywriting book, a 300-article help centre, a big reference-ad library, all past outputs | The host's file search (Claude Projects, ChatGPT file search, Gems); our own hybrid index only inside the factory |
| **digest** (map → reduce) | The question is about the **whole set**: themes, counts, trends. Top-k retrieval returns anecdotes, not counts. (Our inference; the chapter doesn't say this.) | 5,000 reviews, 40 call transcripts, ticket exports | 09 §4 five stages; digest goes in the reference block |
| **query** | The answer is a **number from a table** | Units sold, ROAS by ad, refund rate | Model writes formula/SQL/pandas → tool runs it → model writes up result, showing the query ("RAG with tabular data") |
| **agent** | Passes the 05 §1 test **and** the next source or step really depends on what was found (multi-hop), **and** a workflow version measurably fails | Ad-account watcher that proposes changes; competitor research across unknown pages | Ladder step 8 only, plan-approval pattern, step and cost caps |

Rule of thumb for listing authors: **try stuff first. Use key lookup before similarity search. Use a digest for "across all", a query for "how many", retrieval only for "find the passage", and an agent only when the path can't be written down.**

## 4. What it changes in what we already wrote

### 05_PRODUCTION_PRINCIPLES
- **§1 (workflow or agent): confirmed and given a number.** The chapter's 95% → 60% → 0.6% compounding gives the step cap a numeric basis. Add: "if the branch condition can be written down, it goes in code." Keep our stricter label test; the book counts any tool user, even ChatGPT or plain RAG, as an agent, and we should **not** use that for site labels.
- **§3 (one agent or several): reconcile.** The book calls planner + validator + executor a multi-agent system. We should say these are **components of one agent**. Only a separately prompted model with its own context counts as a second agent and needs `split_reason`. The validator usually earns its place under "you need an independent checker".
- **§4 (memory): compatible, add one rule.** The book's three kinds (internal / short-term / long-term) sit next to our four (short-term / episodic / semantic / procedural): our last three are all "long-term" in the book's terms. Add the **placement-by-frequency rule** and the **short-term budget split** (for example, reserve a fixed share of the context budget for retrieved material). Add a FIFO warning: never trim the goal or brief; it stays pinned.
- **§5 (context budget): extend.** Add `context.mode` and the stuff-first rule with the 30k-token proposal. Note that "huge documents are split into pieces, each handled in its own call, then combined" is the digest mode, which is different from retrieval.
- **§6 (tool calling): sharpen.** Add `kind: read|write` and `automation: auto|approve|human_only` per tool, tool modes per step (`required/none/auto`), "print the parameters used", and "tool descriptions and simpler functions are the first fix for planning errors".
- **§11 (retrieval): mostly confirmed; three corrections or additions.**
  1. Hybrid search should be **term-first** for our data, not "meaning plus exact words" as equals. Many of our lookups are by key and need no similarity at all. Add "lookup by key" as fix #0.
  2. "Split chunks" is solved by **record-based chunking**, not overlap tuning.
  3. Add **contextual retrieval** (entities and "questions it answers" as metadata; a situating header per chunk) as fix #5, and **query rewriting may return unresolvable**.
  The debug order in §11 matches the book's component-by-component evaluation; keep it.
- **§12 (brand brain): extend** with typed insert/merge/replace proposals and the rule that contradictions in prices are settled by effective date and owner approval, not by recency. Add: the glossary also powers query expansion.
- **§13 (cost): add** the book's warning that re-embedding changing data costs money and vector DB spend can reach a fifth to half of model spend. This is the reason we don't run vector infrastructure.
- **§16 (evals): extend** with `must_retrieve` recall, judge anchor examples for consistency, and the agent metrics below.
- **§21 checklist:** add rows for "context mode declared" (all levels), "retrieval recall check" (where mode = retrieve/key), "completion counted in code" (routine, workflow, agent), "plan validated in code before execution" (agent).
- **§22 item.yaml additions (proposal):**
  ```yaml
  context:
    mode: stuff            # stuff | key | retrieve | digest | query | agent
    budget_tokens: 30000
    retrieved_share: 0.3   # max share of budget for retrieved material
  retrieval:
    first_pass: term       # term | embedding | hybrid
    chunking: record       # record | section | fixed
    contextual_headers: true
    rewrite_may_refuse: true
  tools:
    - name: meta_insights
      kind: read
      automation: auto
      report_params: true
  eval:
    must_retrieve: tests/golden/*/expected_ids.yaml
    agent_checks: [valid_plan_rate, invalid_tool_rate, invalid_param_rate,
                   wrong_value_rate, goal_met, constraints_met,
                   completion_verified_by_code, steps, cost, wall_time]
    judge_anchors: tests/anchors-v1/
  ```

## 5. What we should not adopt (and why)

- **A vector database service, at launch or for users.** Our stores are small enough that BM25 plus exact in-memory similarity is plenty. Vector DB cost and re-embedding are real ongoing bills, and we store no user data, so there is nothing of theirs to index on our side. Users get retrieval from their host (Projects, file search, Gems).
- **ANN algorithms (HNSW, IVF, PQ, LSH, Annoy).** They only matter at millions of vectors, which we don't have. Never.
- **End-to-end finetuning of retriever, embedding model or generator.** The book says it helps, but it needs training data, infrastructure and money we don't have. 05 §14 "almost never" holds. Never at our size.
- **Tokenizer-based chunking.** It locks the index to one lab, and we test four.
- **Image-embedding (CLIP-style) retrieval.** Tags and captions from our own taggers are cheaper, explainable and testable. Later at most.
- **Recency reranking for prices and offers.** It would down-weight old prices rather than exclude them. Use hard filters.
- **The book's broad definition of "agent" for site labels.** It would turn every RAG prompt into an "agent" and break our honest labelling.
- **Large tool inventories (Gorilla-style hundreds of APIs) or general web-browsing tools in our listings.** Fewer, clearer tools; browsing conflicts with "no scrapers or logins" and opens the agent to indirect injection. Only official, read-only APIs, with content treated as data.
- **Self-growing skill libraries (Voyager) or reflection-written memory that saves without a person.** One bad lesson repeats with confidence (05 §4). Proposals only.
- **RL planners or finetuned planners.** Expensive, and prompting plus validation is enough for bounded agents. Never.
- **Running code interpreters or text-to-SQL against users' live databases from our side.** It is a code-injection and data risk, and against our no-data rule. These run only in the user's own host or sandbox, on exports.
- **Generating many plans in parallel and picking one.** Costly; only if a model test shows a clear gain within caps. Later at most.

## 6. What we teach users (Learn / Make it yours)

**Beginner**
1. *"Why the AI made it up."* Missing context, not a dumb model: the chapter's opening idea. Show one listing run with and without the brain card.
2. *"Just paste it."* If what the job needs is a few pages, put it all in. Stuffing is fine and often best (the under-200k-tokens guidance, with our own lower budget for cost).
3. *"Never let the AI do the sums."* Use the mini tool or a sheet formula, and ask the AI to show the formula. The 199,999 ÷ 292 example in our own words.
4. *"Check what it pulled."* After a connector run, read the footer: which account, which dates, which level. Wrong dates are the most common silent error.

**Intermediate**
5. *"Paste, look up, summarise or count?"* The five-way decision from section 3 with one ecommerce example each: brain card (paste), current offer (look up by name), 5,000 reviews (digest), units sold last week (count with a formula), what the book says about headlines (search).
6. *"Cut on the seams."* Split material on its natural units (one review, one claim with its exceptions, one book section), never every N words, and give each piece an ID.
7. *"Label your pieces."* Tags, the product names in each piece, and the questions it answers. That is what makes Project or file search find the right part.
8. *"Make it say I don't know."* Add the "if it's not in the brain, ask" line, and test it with a brief that names a sale that doesn't exist.

**Advanced**
9. *"Prep a book for look-ups."* Section split + a two-line header per section + your style guide as the always-on summary, then a copying check (09 §5).
10. *"Ask your data questions with formulas."* Give the AI column names and five sample rows; it writes the formula or SQL; you run it; it explains the answer.
11. *"Test the search, not just the answer."* For 10 questions, write down which pieces should be found, then count how many were. A low count means fix the search before you touch the prompt.

**Expert**
12. *"Plan, check, then act."* Build an agent that writes a plan first. A rule checks the plan (only allowed tools, step limit, budget), you approve it, then it acts. Mark which actions it may take alone, which need your OK, and which only you do.
13. *"Why ten steps is risky."* Compounding errors: 95% per step leaves about 60% over 10. Keep agents short, add checkpoints, and compare against the plain workflow.
14. *"Did it really finish?"* Count the outputs in code; never trust the agent's own "done".
15. *"Fewer tools, better agent."* Remove one tool at a time and see if results drop. Merge tools that are always used together.
