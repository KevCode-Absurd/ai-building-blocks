# Chapter 8: Dataset Engineering: notes and how we use it

> Our mapping of one chapter of Chip Huyen's *AI Engineering* (O'Reilly, 2025) onto our stack, written 2026-10-18.
> The reader's section-by-section summary of the book (section 2) is left out on purpose, so sections run 1, 3, 4…; these notes keep only how the ideas apply to us.
> Book section names are given so the original can be found. The master is `../10_AI_ENGINEERING_FRAMEWORK.md`; where they differ, it wins.

## 1. The chapter in brief

The chapter argues that, now that few teams train models from scratch, the data you curate is where most of the difference comes from. It covers three things. **Curation**: what data, how good, how varied, how much, and where it comes from (annotation guidelines being the hardest part). **Synthesis**: rule-based, simulated and AI-generated data, how to verify it, where it fails (bad quality, surface imitation, collapse, unclear lineage), and distillation. **Processing**: inspect, deduplicate, clean and filter, format.

The chapter is written for people who finetune. We almost never will (05 §14). It still matters a great deal to us, for one reason the book states itself: **the guidelines and data for evaluation are the same as those for training**. Our golden sets, test brands, synthetic test inputs, the intake engine's card data and the Make it yours data-prep track are all dataset engineering. The chapter shows four gaps in our plans. (1) Our "3 kinds of business" are really one kind: three supplement D2C brands. (2) We have no written annotation guideline for test cases. (3) Our "fix until it beats the original" step overfits to the very cases it is graded on. (4) We have no rules for making and checking synthetic test inputs. It also gives us exact methods for steps 6, 7 and 10 of Make it yours.

## 3. How we apply it: by building-block level

### 3.1 Prompt
- **Book:** coverage of phrasing (Data Coverage); a little good data beats a lot of noise (Data Quality).
  **Lands:** 05 §21 "light (5 inputs)"; 06 §8 step 5 ("5 inputs for prompts").
  **Changes:** raise the minimum from 5 to **9 cases: 3 kinds of business × (normal, hard, edge)**. Five cases cannot cover 3 businesses × 3 difficulties, so the "any business" claim isn't earned. Cost: 9 × 3 models × 2 repeats = 54 cheap calls, well under $1–2 per round.
  **When:** launch (W1–2, with `run-test`).
- **Book:** remove examples that teach unwanted behaviour (Data Curation intro).
  **Lands:** `check-item` "won't adopt" scan (06 §5.6).
  **Changes:** run the scan over `references/` and in-prompt examples too, not just instructions. Add a judge criterion "does anything the brief didn't ask for" (extra upsells, unasked rewrites).
  **When:** launch.

  **Lands:** `tests/checklist.yaml`, judge rubric (05 §16, §22 `eval.judge_rubric`).
  **Changes:** each skill gets `tests/guideline.md` (format in §3.8). It covers what good means, anchored definitions of fully / partly / not, "correct but unhelpful" cases, and tie-breaks. The same file feeds the judge prompt *and* the Make it yours test set builder.
  **When:** launch; the first one is written for `website-claims-extractor` in W1–2.
- **Book:** consistency between annotators; plot scores per annotator (Data Quality; Inspect Data).
  **Lands:** `grade`.
  **Changes:** report the score distribution per judge lab and an agreement check. Kevin hand-grades 5 outputs per section bank; if judge and Kevin disagree on more than 1 in 5, rewrite the guideline before trusting the judge.
  **When:** launch.
- **Book:** contamination via duplicates (Deduplicate Data).
  **Lands:** 05 §16's last bullet.
  **Changes:** `check-item` computes 5-gram overlap between `tests/golden/` and `examples/` + `references/`; any overlap above 30% of a case's words fails.
  **When:** launch.

### 3.3 Routine

  **Changes:** each routine's test set adds **failure-mode inputs made by rule**: an empty pull, stale data (yesterday's date missing), a duplicated row, a currency switch, and an API error from the mock connector. Expected behaviour: say so plainly, never guess.

- **Book:** the Llama 3 pipeline, where every stage has a check and failures are re-prompted with feedback (Instruction data synthesis).
  **Lands:** 05 §16 "grade the parts"; workflow pages.
  **Changes:** workflow test sets = **end-to-end cases (≥ 9)** + **per-stage cases (≥ 5 per stage)**, with structured handoffs checked at each stage. Fix loops follow the book's pattern: re-prompt with the failed output and the exact check message, keep only passing outputs as examples.
  **When:** launch for brand brain → static ads → copy.

### 3.5 Agent
- **Book:** tool-use data needs observed (not described) human paths, plus simulation; AI can simulate APIs (StableToolBench); self-play (Data Curation intro; Simulation; AI-Powered Data Synthesis).
  **Lands:** 05 §17 `red_team_tests`; agents from May 2027.
  **Changes:** (a) record Kevin doing the Meta review by hand once (step 0) as the reference path; (b) build `mock-meta`, a simulated connector serving the synthetic sample account (planted patterns) and logging the writes it is asked for; (c) an AI-played "user" for multi-turn agent tests; (d) agent test set ≥ 15 cases + ≥ 10 red-team; grading includes the path (right tool, no needless calls) against the efficient path found in simulation.

### 3.6 App (mini tools, starter app, data prep)
- **Book:** rule-based synthesis with templates and random generators; functional verification beats AI verification wherever it's possible (Rule-based; Data verification).
  **Lands:** FINAL_PLAN §6 "worked examples… one formula, five ways"; `build-mini-tool`.
  **Changes:** add a **property test**: 500 random valid inputs per mini tool (plus boundaries: 0%, 100%, negative margin, zero orders, very large numbers, other currencies) run through every way, each compared with the formula file to the cent. Hand-checked worked examples stay (≥ 12 per tool, 3 of them edge cases). The "in your AI" way gets **simulated-user multi-turn tests** on all four labs: a model plays the user with hidden numbers, and a code check compares the final answer. Every "this looks wrong" report becomes a worked example.
  **When:** launch (Gate A requires the first 4 mini tools to agree in all five ways).
- **Book:** inspect → dedupe → clean → filter → format, keep raw, trial runs, order by cost (Data Processing).
  **Lands:** 09 step 6 (pull, clean, protect, tag, digest), 09 §4.
  **Changes:** the five stages become **seven: pull → inspect → dedupe → clean → protect → tag → digest**. Inspect = counts, length and rating distributions, by source and month, plus 15 minutes reading 20 rows. Dedupe gets its own stage *before* tagging, because tagging costs money: exact text, near duplicates such as the same review syndicated across apps, and copy-paste spam. Clean adds normalising numbers, currency and dates, and stripping HTML from exports. Never edit in place: `raw/` → `clean/` → `tagged/` → `digest/`. Trial on 100 rows first. **Tagging gets its own mini guideline** (tag definitions plus one example each). The "check 20 rows by hand" step becomes measurable: if fewer than 16 of 20 tags match your own, rewrite the tag guide and re-tag. Tag at most about 25 rows per call so rows in the middle don't get skimmed.
  **When:** launch for reviews; Feb–Apr for transcripts, tickets and surveys.
- **Book:** synthetic data for privacy (Why Data Synthesis).
  **Lands:** the review miner / tagger / digest builder demos and tests; DECISIONS open question 7.
  **Changes:** build a **planted-pattern review set**: about 300 reviews, generated from templates plus an AI rewrite, with known theme counts (for example 40 "too sweet", 25 "shipping slow", 10 near-duplicates, 15 with PII, 3 with hidden instructions). The digest must recover the counts within ±10%, strip every PII item, ignore every injection and drop the duplicates. The truth is known because we planted it. Label it as sample data. This also gives lessons a safe demo dataset.
  **When:** launch (W5–10, with review data prep).

### 3.7 Platform (factory, site, intake, data)
- **Book:** the dataset curation loop (find → filter → set aside → rewrite → fill gaps by templates → annotate) (Data Acquisition and Annotation).
  **Lands:** intake engine stages 4–7 (08 §1).
  **Changes:** the intake report gets a **gap map**: which areas, jobs and ladder steps had zero cards this month. That drives targeted sourcing, like the book's "not enough data for topic X". Sources are chosen to fill gaps, not just because they turned up.
  **When:** v0 report (W5–7) shows per-source gaps; the monthly gap map comes with v1 (Feb–Mar).
- **Book:** dedupe at document, intra-document and cross-document level (Deduplicate Data).
  **Lands:** 08 §9 v1, "same link or content only read once".
  **Changes:** v0 already gets exact-hash plus normalised-text fingerprints of sources (cheap). Card-level dedupe compares each new card to existing cards and listings by embedding similarity, then a cheap model confirms. Cross-creator repeats increment a `seen_in` count on the card (consensus signal) and credit the earliest source.
  **When:** source fingerprint at v0 (W5–7); card dedupe at v1.
- **Book:** back-translation as verification (AI-Powered Data Synthesis).

A card fails if the pointer is wrong or the passage doesn't support it. The pointer check is code; the support check is GPT. This turns "zero invented cards" into something measured.

  **When:** launch (field); the ratio is checked from Gate B.
- **Book:** the data flywheel (Data Acquisition and Annotation).
  **Lands:** site v0 votes, "it worked / didn't", comments, "this looks wrong".
  **Changes:** a weekly routine turns public failure reports into new test cases, rebuilt on public test brands. We never use the commenter's own business data; we rebuild the situation on a public brand. Each one is logged as `added_reason: user report <link>`.

### 3.8 The test-set standard (proposed v1, for every listing)

**Files**
```
tests/
  guideline.md       the annotation guideline (shared by judge, Kevin and the test set builder)
  golden/cases.yaml  the cases (schema below)
  checklist.yaml     code checks + judge criteria (exists)
  model-runs.csv     (exists)
```

**Case schema** (each case):
```yaml
- id: adcopy-014
  bank: creative/ad-copy          # shared case bank this case belongs to
  business: ecommerce-d2c | software | service-creator
  brand: gruns                    # public test case, saved source pack
  difficulty: normal | hard | edge | trap
  slices: [thin-brain, vague-brief, typos, strict-claim-rule, long-input, other-currency]
  origin: real-public | augmented | synthetic
  generated_by: <model id>        # required if not real-public
  split: dev | heldout
  input: {brief: "...", brain: test-brands/gruns/brand-brain@v2, refs: [...]}
  expected:
    must_include: [{fact: "...", source_id: C-04}]   # every fact must be in the input bundle
    must_not: ["any price except $X", "health claim not in register"]
    planted_truth: {...}          # for synthetic data with known answers
    why: "tests a product with no reviews"
  verified_by: kevin | gpt-check+kevin
  added: 2026-11-03
  added_reason: initial | failure round 2 | user report <link>
```

**Size by type** (minimums; the dev / held-out split is roughly 2:1):

| Type | Minimum cases | Plus |
|---|---|---|
| Prompt | 9 (3 businesses × normal/hard/edge) | 2 paraphrases of 1 normal case |
| Skill | 15 (per business: 2 normal, 1 hard, 1 edge, 1 trap) | paraphrase pair for 3 normal cases |
| Routine | 15 | 5 rule-made failure inputs via mock connector |
| Workflow | 9 end-to-end | 5 per stage |
| Agent | 15 | 10 red-team; reference path for 5 |
| Mini tool | 12 hand-checked worked examples (3 edge) | 500 random property inputs; 5 simulated-user dialogues per lab for "in your AI" |
| Intake engine | 20 hand-marked sources | 10 trap sources |

This reconciles three different numbers in our own docs (05 §21: 5; 05 §16: 10–30; 09: 10–20). Cost check: a skill's 15 cases × 3 models × 2 repeats = 90 runs plus judge calls. At C1/C2 prices that is a few dollars a round, inside the $25 cap. C3 runs on dev cases only until the final gate.

**Coverage matrix** (`check-item` enforces it):
- Every business kind has ≥ 3 cases (≥ 2 for prompts); each difficulty has ≥ 2; at least 1 trap (hidden instruction in content) for skills and up.
- At least 1 case each for: no brain or thin brain; vague one-line brief; messy input (typos, pasted export); strict claim rule; and for /ecommerce versions, a price conflict between two pages.
- Board versions add ≥ 5 cases of their own industry; general cases are reused, not copied.
- Use pairwise coverage across slices, not every combination.

**Shared case banks.** Cases live in per-function banks (`test-banks/creative/ad-copy/`, `test-banks/brain/`, ...), so 20 ad listings reuse one bank of 15 briefs and only the `expected` block is specific to each listing. This cuts annotation time by roughly 5–10× and makes listings comparable.

**Annotation guideline** (`guideline.md`, one page):
1. The job in one sentence, and who reads the output.
2. Must-haves, each tied to a checklist line (code-checkable ones marked).
3. Fails outright (the costliest mistake: invented claim, wrong price; things not asked for).
4. Fully / partly / not definitions per judge criterion, each with one short anchored example.
5. Edge rulings: correct but unhelpful = partly; refusing on missing data and saying what's missing = fully; extra unasked content = partly at best.
6. Facts rule: an expected answer may only use facts in the case's input bundle.
7. Version and date; a guideline change re-grades the bank.

Consistency check: Kevin and the judge independently grade 5 outputs per bank. If they disagree on more than 1 in 5, rewrite the guideline.

**Real vs synthetic.** Normal cases are `real-public` (saved pages of public test brands) or `augmented` (a real case with one thing changed). Synthetic cases are allowed mainly for hard, edge and trap cases and for planted-truth data. Cap synthetic at half of any bank.

**Verifying synthetic cases** (all must pass before a case counts):
1. Code: schema valid; every `must_include` fact traces to a source ID in the input bundle; planted truth recorded; no 5-gram overlap with examples or references.
2. Heuristics: not empty or extreme in length; no near-duplicate of another case; no two cases with the same input and different expected answers.
3. Cross-lab verifier: a model from a different lab from `generated_by` confirms the case is realistic, tests what `why` says, and that `expected` follows from the input.
4. "Spot the synthetic": once per bank, mix 5 real and 5 synthetic briefs. If a model or Kevin picks the synthetic ones at 5/5, make them messier.
5. Human: Kevin reads every synthetic hard, edge or trap case (the counts are small).

**Gates and reporting.**
- `grade` reports by slice (business, difficulty), not one average.
- Publish gate: costliest mistake = 0 on every case; each business kind within ±5 points of the others (FINAL_PLAN §9 "Same score ±5"); held-out score within 5 points of dev score. A bigger gap means step 8 overfitted.
- Pairwise A vs B is run in both orders; a win counts only if both orders agree.

**Held-out split.** Step 8 ("fix until it beats the original") sees only `dev` cases. `heldout` is run once at the gate, and when it fails, new held-out cases replace the ones that leaked into fixing. Published downloads (09 "every listing's own test set as a download") contain the dev split only.

## 5. What we should not adopt (and why)

- **Pre-training, full finetuning, training from scratch, ossification worries, data-mix scaling experiments.** We are API-only with a small budget. None of these apply.
- **Hiring annotators, annotation platforms or data marketplaces.** One founder plus Claude, free-first. Our "annotators" are Kevin (spot checks) and cross-lab models under a written guideline.
- **MinHash, Bloom filters or vector-search dedupe infrastructure.** Our datasets are tens to low thousands of items. Pairwise exact, n-gram and embedding comparison is enough. Revisit only if the intake card store passes about 20K cards.
- **Active learning, importance sampling, data pruning.** These solve having too much data. Our problem is too little, carefully checked.
- **Public review or benchmark datasets (Hugging Face, Kaggle and so on) as lesson or test material.** Licences are often research-only or non-commercial, the site will carry ads, and provenance is murky. Use our own planted-pattern sets and saved public pages.
- **User data as a flywheel.** It conflicts with "no user business data stored". Use public signals rebuilt on public brands instead.
- **Distilling one lab's outputs into another model for our own production.** Most terms forbid it for competing models; we have no high-volume step that needs it; and the superficial-imitation risk is real. Teach it (step 10, with a terms warning); don't do it.
- **Self-improving loops that retrain on our own outputs** (bootstrapping). Llama 3 found unverified self-training harmful, and we have no training loop anyway. The runtime equivalent (lessons auto-approved) is already banned in 05 §4.
- **Training AI-content detectors or acceptance classifiers** as verifiers. Too heavy. The lightweight "spot the synthetic" check gives most of the value.

## 6. What we teach users (Learn / Make it yours)

**Beginner**
- *"Your test set is a small dataset. Treat it like one."* (step 2) Why 10–20 cases beat 100 random ones; the 3×3 grid (kinds of situation × normal / hard / edge); write the "why this case" line for every case.
- *"Write down what good looks like before you grade."* (steps 1–2) A one-page guideline: must-haves, instant fails, what "partly" means, one example each. The same page works for you, a helper or an AI judge.
- *"Don't let your examples leak into your tests."* If a test brief is also in your prompt's examples, your score is fake.

**Intermediate**
- *"Prepare your data in seven steps."* (step 6) Pull → look (counts, lengths, 15 minutes reading) → remove duplicates → clean (formats, HTML, currency) → protect (strip personal details, keep raw) → tag (with a tag guide; check 20 rows; redo if fewer than 16 match) → digest. Never edit the original. Try 100 rows first. Practise on our sample review set, where you can check your digest against the planted answers.
- *"Make hard cases on purpose."* Take a real case and change one thing: a missing field, a typo-filled brief, a price that differs between pages, a review with hidden instructions. Swap a name or gender to test bias.
- *"Using AI to write test cases, safely."* Generate a few per situation, not many; label them as AI-made; check with a model from a different company; read the hard ones yourself; mix in real cases.
- *"AI judges prefer the first answer."* Run A vs B both ways round and count only consistent wins.

**Advanced**
- *"Teach it your style from your own best work."* (step 7) Reverse instruction: take your own best copy and have AI write the brief that would have produced it. Now you have (brief, your real copy) pairs for examples or training, with nothing invented in the answers. Copying check stays on.
- *"Check what AI tells you by translating back."* For summaries, cards and docs: can you get from the summary back to the exact passage, and does that passage support it?
- *"Simulate before you connect."* Test a routine or agent on a sample account with planted problems before it touches your real ad account.

**Expert**
- *"Training a model: start with 50."* (step 10) Formats (instruction → response; winner vs loser from your A vs B tests); 50 good pairs first, then train on 25/50/100% and plot. Flat means stop. Little data → small add-on (LoRA) on a stronger model. Match the prompt format at use time exactly. Measure on held-out cases only.
- *"Distilling a big model into a cheap one: what really transfers."* Style transfers easily; accuracy doesn't. Use only outputs that passed your checks. Read your provider's terms first.
- *"Why AI-made data alone eventually goes wrong."* Model collapse and bias loops, in plain words: keep real data in the mix and record where every example came from.
