# Chapter 10: AI Engineering Architecture and User Feedback (plus Epilogue): notes and how we use it

> Our mapping of one chapter of Chip Huyen's *AI Engineering* (O'Reilly, 2025) onto our stack, written 2026-10-18.
> The reader's section-by-section summary of the book (section 2) is left out on purpose, so sections run 1, 3, 4…; these notes keep only how the ideas apply to us.
> Book section names are given so the original can be found. The master is `../10_AI_ENGINEERING_FRAMEWORK.md`; where they differ, it wins.

## 1. The chapter in brief

The chapter pulls the whole book together into one reference architecture, built up in order. Start with the bare minimum (query → model → answer), then add components only as needs appear: (1) richer context through retrieval and tools, (2) input and output guardrails, (3) a router and a model gateway, (4) caches, (5) agent patterns with loops and write actions. Monitoring and observability are not a sixth step but something designed in from the start, and orchestration is the glue that chains the parts. The second half argues that user feedback matters more in AI products than in normal software, because it is both a quality signal and the only proprietary data most teams will ever own. It lists the feedback you can read out of conversations, says when and how to ask for it, and warns about its biases and the loops it can create.

Why it matters to us: this gives us the "build-up" spine every listing is missing. Our ladder (0–8) and our six types already go from simple to complex, but nothing yet says **which component gets added at which step, and what has to pass before the next one is added**. The feedback half maps almost one-to-one onto decision 13 (▲ Useful, "it worked / it didn't", ▲▼ on comments, private stars, kits). The monitoring half fills the biggest gap in our routine and agent plans: silent failure and drift.

## 3. How we apply it: by building-block level

### 3.0 The build-up framework (one spine for every listing)

**Rule:** a listing adds a component only when (a) the previous step's check has passed, and (b) the component names the failure it fixes and a with/without run on the golden set shows that it fixes it. This adapts the chapter's "add components as needs arise" (AI Engineering Architecture) to our ladder.

Our order differs from the book's on purpose: **output code checks come first, at step 1**, not after context, because "zero wrong prices and zero invented claims" is a hard rule from the first prompt. Input guardrails arrive with outside content (step 2). The router and gateway are **factory infrastructure** we use at every step. They are not a listing component until hosted runs exist.

| Ladder step | Typical type | Component added (book step) | Check that must pass before the next step |
|---|---|---|---|
| 0 By hand | (none) | Baseline: written "what good looks like" checklist and 5 real inputs | `tests/checklist.yaml` exists with the costliest mistake named; 5 golden inputs on 3 kinds of business |
| 1 Ask | Prompt | Simplest form: one model call, context in cache order (`05` §5), **output guardrails**: format, empty-output, banned claims, price match (Step 2, output) | Light golden set: costliest mistake = 0; code checks 100%; judge "fully" ≥ 80%; recommended model picked (cheapest within 5 points) |
| 2 Connect | Skill (+ MCP connector, read-only) | **Enhance context** (Step 1): brand brain card, references on demand, data digest, connector reads. **Input guardrails** (Step 2, input): retrieved content treated as data, personal data stripped before the call, injection tests | With/without-context run shows a gain (≥ +5 points or a costliest-mistake drop); "is the fact current?" check passes; 3 injection inputs and 3 false-refusal inputs pass |
| 3 Save | Skill or prompt writing to a sheet | Typed, stable output; the sheet acts as the user's **exact cache** of results (Step 4, exact) | Output validates against its `_types.yaml` schema on 100% of golden runs; re-running doesn't duplicate rows (idempotent write) |
| 4 Schedule | **Routine** | **Monitoring** (Monitoring and Observability): Log tab heartbeat, empty-data guard, stale alert, change alert; model and version recorded per run | 5 scheduled runs in a row, each with a log line; a forced failure (expired connector, zero rows) raises a visible alert, not a silent "all fine" |
| 5 Mini app | App (mini tool / mini app) | Interface, plus **feedback capture** ("it worked / it didn't" link with version); key kept off the page; per-run cost cap | App result matches the listing result on all worked examples; cap enforced in a test; the feedback link carries listing ID and version |
| 6 Full app | **Workflow** | **Orchestration** (AI Pipeline Orchestration): typed handoffs between stages; **cheap-first routing** per stage (Step 3, our internal rule); traces per run | Every stage passes its own golden set; each handoff validates (a missing field fails loudly); one trace per run with cost and time per stage |
| 7 Share | App / workflow for a team | Gateway duties in the user's own setup (Step 3, gateway): access per person, per-person spend caps, who sees whose feedback | Permission test: a teammate without access can't run the write step; per-person cap triggers in a test |
| 8 Act | **Agent** | **Agent patterns** (Step 5): loops, next-action choice, **write actions** behind approvals, step cap, human hand-off | `red_team_tests[]` pass; every write has approval + idempotency key; a loop test hits the step cap and stops; N failures hand to a person |

**By type** (the minimum each type ships with, cumulative):
- **Prompt:** model call · cache-order context · output code checks · empty-output check · version line.
- **Skill:** + context construction (brain card, `references/` on demand) · input guardrails · hard rules named with where they're enforced · full golden set · false-refusal inputs.
- **Routine:** + trigger · heartbeat log · empty/stale/change alerts · pinned model record · failure policy (retry once, then alert).
- **Workflow:** + typed handoffs · per-stage model class with cheap-first escalation · per-stage evals · trace per run · "redo one stage" instead of rerunning everything (the inpainting idea, Feedback Design).
- **Agent:** + loop and step caps · approvals on writes · idempotency · red-team suite · human hand-off after N failures or N turns · loop detection (same tool call three times = stop; the chapter's dialogue-diversity idea).
- **App:** + interface · server-side key · cost cap · feedback capture with version · access control once shared.

### 3.7 Platform: factory, site, intake, data

**Gateway (factory).** One file, `tools/lib/models.ts`, exposing `callModel({ modelClass | modelId, messages, maxTokens, temperature, runId, stepId })`. It:
- wraps the four labs' SDKs, loading only the four keys by name (DECISIONS 2026-10-18);
- enforces $2 per run and $25 per round before each call, using estimated tokens × `_models.yaml` prices;
- writes one ledger row per call (the Creative Engine cost-ledger format): exact model ID returned by the API, sampling settings, prompt template version and hash, input and output tokens, cached tokens, latency, cost, runId, stepId;
- retries on rate limits or 5xx (max 2, with backoff), then **fails loudly**. **No automatic fallback to another lab during model tests**: a silent swap would make the test results false. Fallback is only for later hosted runs (v3), if ever.

This is the book's gateway (Gateway), built in-house. **It is not a router service.** It goes into Launch, W2, inside `run-test`.

**Routing: internal cheap-first rule vs third-party router.** These are two different things, and only the first is allowed:
- *Internal cheap-first rule* (allowed): a deterministic rule written in `item.yaml` and run by our code or by the user's own setup: "run the step on C1; if a code check fails or the judge scores below threshold, re-run on C2, then C3; log each escalation." If more than 30% of golden runs escalate, the step's default class goes up one. It also checks token count before the call, and moves up a class (or chunks the input) when the input exceeds the cheaper model's context window (Router, context limits). No classifier and no third party: it is a policy, like the existing C4 "top plans, cheap repeats". It makes the "Recommended = cheapest within 5 points" result usable at run time.
- *Third-party router* (not allowed): OpenRouter, LiteLLM proxy, Portkey, Martian/NotDiamond-style learned routers, Cloudflare/Kong gateways. These are excluded by the 2026-10-18 decision. **Correction needed:** `05` §10 still tells users they can run "through a router such as OpenRouter, LiteLLM or Portkey"; `06` §3.1 says `run-test` runs "via the router"; `04` §4 has `routers_ok[]` and `runs_in[] … router`. These should be reworded to "gateway wrapper" and "cheap-first rule", or removed.
- *Intent routing on the site* (the book's intent classifier) is done without a model: filters, search and the "Where are you today?" chips. The intake engine's "decide what each becomes" stage is the one place a model classifies: a C1 model choosing from fixed categories, with a "not sure, send to Kevin" option (the book's ambiguous-query case).

**Caching (factory).**
- Provider prompt caching: keep the `05` §5/§13 order. Record `cached_tokens` per call so the hit rate is measured, not assumed.
- **Exact cache** in `run-test`/`grade`: key = hash(prompt hash + input hash + exact model ID + settings). Re-grading or re-building a report reuses the stored output instead of paying again. The cache is cleared per listing version. This stretches the credit budget (Step 4, exact caching).
- Intake: cache transcripts and fetched article text by URL plus date, so a re-run doesn't re-read the source.
- Never semantic caching (see §5).

**Monitoring (platform).** Define our own MTTD, MTTR and CFR:
- **CFR** = share of listing version releases that need a fix or rollback within 30 days (triggered by an "it didn't" spike, a failed monthly re-test, or a found wrong price). Shown in the quarterly report next to the published import fail rate.
- **MTTD** = time from the first "it didn't" report or failed re-test to triage. Target: 2 working days, the same as the comment-reply target.
- **MTTR** = time from triage to a fixed, re-tested version, or a "known issue" banner on the listing. Target: 7 days.
- **Weekly canary run:** about 10 published listings' golden sets on each lab's cheap model (estimated well under $3 a week). It catches provider drift between the monthly re-tests (Drift detection, model changes). Any score drop above 5 points triggers a full re-test of affected listings.
- **Reading by hand:** each section review includes reading 10 raw outputs (top 5 and bottom 5); each new kind of failure becomes a code check or golden input (the Shankar et al. point in Logs and traces). This confirms `09` §6 "Your eye".
- Every metric splits by listing, version, model ID, tool and business type (Metrics).

**Feedback design (site): our signals mapped to the book.**

| Our signal | Book category | How we use it | Bias to manage |
|---|---|---|---|
| **It worked / It didn't** (listing, per version) | Explicit, the "did we solve your problem?" kind; strongest | Main quality signal after our test score; feeds the fix queue; ranking input | Unhappy users report more (response bias): show the ratio only after 10 reports, always with counts ("worked 87 · didn't 4") |
| **"It didn't" form** | Explicit + structured complaint (Complaints) | Required: tool (Claude/ChatGPT/Gemini/Codex/other), model if known, ladder step, business type, version (auto-filled). Category, one of: couldn't install or run · didn't know what to give it · **made something up / wrong number** (the costliest mistake, triaged first) · too generic for my business · wrong length or format · refused · other. Free text optional, with a "don't paste customer data" note | Leniency: no follow-up interrogation; the category is one click |
| **▲ Useful** (listings) | Explicit, positive only | Sorting (Top, Hot). No downvote on listings, matching the "when something good happens" debate: it's optional and never prompted | Popularity loop: never the first ranking key (test score is) |
| **▲▼ on comments** | Explicit, used to sort advice | Wrong advice sinks | Pile-ons: collapse only at very low scores |
| **Report button** (comments, listings) | "When something bad happens" | Moderation queue; for listings, "unsafe or wrong" goes straight to the fix queue | — |
| **Comments** | Natural-language feedback | Weekly C1 clustering of the week's comments into the same categories as the form (footnote: use AI to analyse feedback); "I meant…" / "it asked me for X I don't have" comments become golden inputs | The model labels, a person checks 20 |
| **☆ Star** (private, count public) | Implicit-ish positive; private signals are more candid (How to collect, visibility) | "Saved 410×" shown; feeds kits | — |
| **Kits / kit → workflow** | Implicit: which listings people chain | Suggests "feeds into" links that `build-graph` missed | Small samples |
| **Copy / download by tool, ladder chip chosen** | Implicit actions (Other conversational feedback) | Anonymous counts only; shows which tools need better exports | Noisy; never shown as quality |
| **"This looks wrong"** (mini tools) | Error report at the moment of failure | Each confirmed case becomes a worked example | — |
| **Return visit nudge** | Feedback built into the workflow | If the browser remembers (localStorage, nothing on our server) that you copied a listing, the listing shows "Did it work?" with two buttons on your next visit | Leniency is low because it's one click |

**Ranking against the degenerate loop** (Degenerate feedback loop): our test score stays the first key (already in deck slide 23). Add an **exposure rule**: newly tested listings get a fixed share of "Top" slots (e.g. 2 of every 10) for their first 14 days, and "Hot" is time-weighted. Shuffle the order of equal-score listings so first position doesn't decide the winners (Position bias).

**Feedback into the factory (the flywheel).** "It didn't" report → fix queue → the case becomes a golden input (anonymised by the reporter's own description, never their data) → fix → re-test → version bump → followers notified ("re-tested and improved"). This is our data flywheel: the moat is **test results plus outcome reports per version × tool × model × business type**, not user content. It also tells us when a board is earned: "didn't work for my business" counts by business type are the demand signal deck slide 24 already relies on.

**Intake.** The intake engine's idea cards can carry a "where this sits in the build-up" field (which component it adds), so the founder's one-page report shows whether an imported idea is a context improvement, a guardrail, a routing rule or an agent pattern.

## 5. What we should not adopt (and why)

- **Third-party routers and gateways** (OpenRouter, LiteLLM proxy, Portkey, Kong, Cloudflare AI Gateway, learned routers). Decided against; four direct lab accounts cover what users use. We take the gateway's functions in about one file of our own code.
- **Trained intent classifiers and next-action predictors.** No traffic to train on and no hosted chat to route. Filters, chips and fixed-category C1 calls are enough.
- **Semantic caching.** The chapter itself doubts it; for us a false match means a wrong answer, and we have no repeated user queries anyway.
- **Parallel duplicate calls to cut latency** (Output guardrails). We are batch and download-first; latency barely matters, and it doubles cost under tight credit caps. Sequential retry (max 2) is enough.
- **Orchestration frameworks** (LangChain, LlamaIndex, Flowise, Langflow, Haystack) in the factory. They hide behaviour and add hidden calls. Plain TypeScript, as the chapter itself advises at the start.
- **Guardrail frameworks** (NeMo Guardrails, Purple Llama, PyRIT) at launch. Our guardrails are specific (claims register, price match, `scan-skill`); a general framework adds weight without catching our costliest mistake. Revisit only if we host agents.
- **"Log everything" for users.** The rule applies to our factory. For users it would break "no user data stored". They keep their own logs; we give them the format.
- **Training or personalising models on user feedback.** We hold no user data, our users are too few, and the sycophancy and degenerate-loop findings argue against it. Feedback changes prompts, tests and rankings, never weights.
- **Private data-donation flows** ("attach your recent data to this report"). That would store business data. Reporters describe their case in words or post it publicly by choice.
- **Side-by-side "pick the better answer" votes from users.** Randomness, length and position bias, and our audience can't always judge. Blind A vs B stays with the cross-lab judge and Kevin.
- **1–5 star ratings, sentiment tracking, conversation-organisation signals, sampled 1% prompts.** We have no hosted conversations and a small audience; stars would suffer from leniency bias, which decision 13 already avoids.
- **Streaming-mode output guardrails.** Not relevant until hosted runs (v3).

## 6. What we teach users (Learn / Make it yours)

**Beginner**
- *Start simple, add one thing at a time.* The build-up as a picture: ask → give it context → check it → save it → schedule it → put a button on it → let it act. "Only add a part when you can say what it fixes."
- *Check the boring failures first.* Did it answer at all? Is it in the right format? Did it refuse something reasonable? These three checks catch more than you'd think.
- *How to tell us it didn't work.* What the "it didn't" form asks and why (which tool, which step), and what happens next (fix queue, re-test, notification).

**Intermediate**
- *Don't send your customers' details to the AI.* Placeholder masking with your own reverse map, using the browser-only mask tool. (`09` step 6)
- *Your corrections are gold.* Keep a "lessons" file of every "No, I meant…" you type, and add the case to your test set. (`09` steps 2 and 4)
- *Cheap first, step up only when a check fails.* How to run the cheap-first rule by hand in ChatGPT/Claude/Gemini, and how to read our "recommended / budget" results. (`09` step 9)

**Advanced**
- *Your routine can fail silently.* Building a Log tab and the empty, stale and jump alerts into a scheduled report; making the first line a health line.
- *Models change under the same name.* Pin dated models where your tool allows it, re-run your test set monthly, and keep the date next to your results.
- *Choosing an automation tool.* The three questions (does it support what I use, can it branch and handle errors, does it make calls I can't see), applied to n8n, Make and Zapier.

**Expert**
- *Observability for your own agent.* One run ID, a step log, approvals logged as steps; MTTD, MTTR and change-failure rate for a one-person team.
- *Feedback without fooling yourself.* Leniency, position, length and popularity biases; why we never let votes alone rank anything; why training on thumbs-up makes models flatter you.
- *Edits as training pairs.* Turning your edited outputs into (input, worse, better) pairs for the training-pair builder, and when that's worth it. (`09` step 10)
