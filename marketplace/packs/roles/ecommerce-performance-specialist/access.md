# Performance access and delivery
Discover the tools actually available in this session. A downloaded pack provides procedures, not a connected browser, hosting account, WordPress admin, paid testing service or deployment permission. Use public URLs, supplied reports and authorized repository files first. Never request credentials in chat.

Bind every observation and change to the merchant, URL/page type, source revision, environment and time. A local fixture, staging preview and production are different resources. Reuse the user's existing authorization within its scope. Prepare reversible code/configuration patches locally or in the authorized staging environment; production writes, plugin installation, CDN purges and checkout transactions need authority covering those operations. Do not infer this from access to a dashboard.

Test orders only in an explicitly identified sandbox/test gateway with external messages disabled or routed to a test sink. A copied production database can retain payment credentials, webhooks, mail recipients and live scheduled jobs: verify isolation before starting it. A missing sandbox is a verification gap, not permission to buy, refund or email a customer.

The exported tools/performance-review.mjs runs offline with Node and reviews supplied measurements; it does not collect them. A browser trace or Lighthouse run needs an available browser/test runner. Use its real help/schema, preserve raw outputs and do not claim a run from a command that was only proposed. No paid API calls are required by this kit.

Keep operational logs private and redact session cookies, customer details and credentials. Pass helpers only the exact files/trace sections they need. Provide native patches, a measurement receipt, functional checks and rollback instructions; state the last independently verified state.
