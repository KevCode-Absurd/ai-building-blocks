# Deliver finished images from approved assets

Use for a finished ad or listing-image request. Start with the actual files: identify each product/variant, source URL or file ID, rights reference, available angles, native dimensions and whether it is photography, an illustration or generated artwork. An existing ad is a visual reference, not independent evidence for its claims or permission to reuse its models/music. Read the original at full size.

Make a buyer-question map before rendering: each requested concept must answer a distinct buyer question or make a distinct supported argument. Different layouts, colours, headlines or crops alone do not establish distinct concepts. An aspect-ratio adaptation belongs to its original concept. A detail image must make the relevant detail larger and more readable than in the overview at the intended display size; three filler layouts from one photograph are not three buyer concepts. Use only substantiated attributes. For listing sets, distinguish the main-image rules from secondary images and A+; verify the current rules for the exact marketplace/category rather than applying one universal size or overlay rule.

Choose a visual mechanism that helps each buyer argument before building the layouts. Depending on the evidence, that might be an atmospheric full-photo composition, an actually enlarged detail, a sequence showing use, a personal-note treatment or a qualified comparison. These are options, not a compulsory template set. Repeating the same photo panel with a different headline is weak art direction even when the written arguments differ. Keep the brand recognizable while varying focal hierarchy, image treatment and reading path where the idea calls for it. Never fabricate product views, human use, packaging, materials or proof to make a concept look different.

Check that each hook's promise is actually fulfilled by its visible content. Record the buyer question, headline promise, supporting source and exact panel/scene that answers it. A specification card does not demonstrate an action; a caption promising a demonstration needs a source-grounded sequence. When the necessary view or footage is missing, revise the promise to what the artifact can show, or mark the concept as awaiting that specific production evidence. Do not rank an unfinished proof sequence as a completed answer to the buyer's objection. Review this meaning as well as legibility before delivery.

Compare a phone-size contact sheet before final export. Temporarily ignore the headlines: if every concept has the same focal point and composition, decide whether that sameness serves the actual brief or whether an idea needs a different visual execution. Inspect the individual designs too. Whitespace should support emphasis and reading, not simply fill a taller canvas; recompose for each requested placement instead of extending a feed layout into a mostly empty Story. A product detail should be visibly larger at that display size, not just described as a close-up. This is a craft review, not an automatic diversity score or a requirement to break a deliberately consistent template series.

Use the permitted brand asset inventory before inventing a replacement wordmark or substituting fonts. Check supplied logo variants and usable licensed font files; if they are unavailable, make the best faithful draft with a disclosed substitute. A fallback used for one job does not become an approved brand standard in memory.

For approved real products, preserve the supplied product pixels/geometry when composing. Use the host's image tool for requested raster generation or edits when available; an illustration or generated reconstruction is not proof of the real SKU. State unavailable native photo/footage dependencies precisely, finish the feasible local work, and do not present a technical schematic as finished photography.

Export the requested files, then open every export at full size and at the intended phone display size. Check headline wrapping, line spacing, cropped glyphs, safe-zone overlays, logos, product edges, and labels against the original. If text is cramped, shorten/reflow it or change the layout; do not merely shrink all type. Re-export and inspect after the final edit. A contact sheet helps compare concepts but does not replace individual export inspection.

Package the editable design/render source, licensed dependencies, final exports, source/claim references and a short placement guide in one handoff directory. Keep image dimensions and source dependencies explicit. Run the delivery check described below only when delivering final media; it does not replace visual review.

For static ad sets checked with `check-creative-set.mjs`, retain its default single-size checks unless the actual brief requests variants. Record those requirements separately in a brief-derived plan: `{"brief":"brief.md#deliverables","concepts":[{"id":"gift","sizes":["1080x1080","1080x1350"]}]}`. Give each creative-manifest entry its `concept_id`, product, angle and format; keep product, angle, format, segment and funnel consistent within a concept. Run `node check-creative-set.mjs <exports> --concept-plan <brief-plan.json>` to opt in explicitly. `--sizes 1080x1080,1080x1350` only permits dimensions; it does not enable concept grouping. The plan requires every requested concept/size and permits one export per aspect. Do not delete requirements or relabel unrelated work to make checks pass. Diversity uses each concept's first requested size; near-copy checks still compare all exports across concepts. Keep the same first requested size across concepts when the brief allows it. A concept label is a grouping declaration, not semantic proof: independently compare the buyer question, headline promise, visible evidence and enlarged detail, then inspect every ratio export. Use the creative checker only for its static-ad scope; it does not replace marketplace-specific listing checks or the separate media-delivery manifest below.

In concept mode, probe each export at its actual render size and key `type-report.json` by its exact export filename, such as `gift-square.png` and `gift-portrait.png`. Shared HTML keys, numeric-prefix matches and inline manifest type declarations cannot establish per-export coverage. Do not copy one probe under multiple export keys; the report records inspection and does not authenticate that inspection.

## Delivery integrity check

Create `manifest.json` beside the handoff's sources, editable project and exports; run `node tools/media-delivery.mjs path/to/manifest.json`. The optional local dependency `ffprobe` measures media metadata; missing support is reported, never counted as a pass. SHA-256 values must come from the actual files after the final edit.

The manifest uses `schema: "media-delivery/1"` and these arrays:

- `requiredSourceKinds`: the actual brief's requirements, such as `["photograph"]` or `["footage"]`. Do not remove a required kind to turn an incomplete deliverable into a pass.
- `sources`: `id, path, sha256, kind, provenance, rightsReference`. Kind is `photograph`, `footage`, `audio`, `illustration`, `generated` or `reference`. Record the evidence for each declaration; the checker cannot authenticate it.
- `editableFiles`: `path, sha256` for the project/render source and its local dependencies.
- `outputs`: `path, sha256, kind` (`image` or `video`), `placement, sourceIds, width, height, review`. Video also has `durationSeconds` and `audioExpected`.
- Each output's `review`: its current `sha256`, `reviewer`, concrete `notes`, and `"reviewed"` only for checks actually completed. Images require `phoneSize, productFidelity, textAndCrop`. Video requires `phoneSize, productFidelity, captions, fullPlayback, sound`. For a deliberately silent export, explain the checked absence of sound; do not claim listening to nonexistent dialogue.

All paths are relative to the manifest directory. An `INTEGRITY_PASS` checks containment, bytes, metadata and the presence of current review declarations. It does **not** certify actual visual quality, product identity, rights, marketplace compliance, full playback or permission to publish. Keep useful completed work moving while the specific missing dependency is held.
