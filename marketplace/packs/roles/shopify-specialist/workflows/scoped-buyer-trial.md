# Keep a buyer trial inside its authorized scope

Use when testing a storefront, checkout or recovery flow in an agreed test environment. A simulated payment is still an action against a specific test resource. Reproduction does not expand the permission granted for the original test.

1. Record the allowed environment, account or dataset, actions and resource-count limit before opening the buyer flow. When the brief allows one new dataset, create it once, persist the returned ID in local working context and use that same ID for all tests and retries. Never silently create a replacement to get a clean result.
2. Inspect startup behavior before loading a fresh browser context. A page may create a dataset automatically when local storage is empty. Supply the authorized session using the documented initialization mechanism before navigation. Observe the network and fail closed on unexpected resource creation or calls to another account, dataset or host. Each viewport, reload and fresh browser context must keep the same scope.
3. Separate read-only evidence checks from transactional replay. Default the delivered verification script to checking saved receipts and independent GET readbacks. Make write mode explicit and bind it to the authorized resource. A script that creates a fresh dataset on every invocation is not a safe replay of a one-dataset trial.
4. Before retrying a transaction, read back the recorded operation and reuse its idempotency key with the same payload. Use new operation keys only for genuinely new authorized cases. Account for state already changed by earlier cases; do not assert a fresh-stock baseline after a completed order or refund without reading it.
5. Exercise the requested success, decline, retry, receipt, cancellation, refund and stock checks within the scope. Keep expected and observed changes distinct. Record any blocked operation without broadening the scope to make it pass. Do not reset a shared server or delete evidence to obtain a clean run.
6. Reconcile the final request log to the allowed environment and resource ID. Include unexpected creation attempts and completed writes in verification, even when all buyer-flow assertions passed. A boundary violation is a separate failure; correct math and attractive screenshots do not cancel it. Deliver the working artifact, scoped reproduction instructions, evidence and exact remaining decision.

These steps apply to the actual permission in the brief. If multiple isolated resources are explicitly authorized, record that allowance and identify them separately. Do not ask again for authority already granted. An offline check, local simulator or sandbox receipt proves only its tested behavior, not production Shopify, payment settlement or message delivery.
