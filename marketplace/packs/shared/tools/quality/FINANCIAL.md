# Financial evidence and arithmetic

For money decisions run `node tools/quality/numbers.cjs context/numbers.json --financial --final <deliverable>`. `qe-check.cjs ... --financial` also requires the ledger and forwards the mode. A ledger object with `"mode":"financial"` enables the same checks. Keep the full data snapshot local to the job; do not embed customer records in the deliverable.

Each figure has `id`, finite `value`, `metric`, `unit`, `period` (`start`, `end`, `timezone`) and monetary `currency`. Windows use valid ISO dates and an IANA time zone. Units are `money`, `money_per_order`, `orders`, `sessions` or `ratio` as appropriate. The precise meaning and grain of each metric must agree with the export. Period net sales divided by orders is a custom KPI; it is not native Shopify purchase AOV.

An input has `source: {file, sha256, pointer}`. File paths resolve relative to the ledger, must remain inside that directory even after symlink resolution, and must contain JSON. The SHA-256 pins the exact bytes; the RFC6901 pointer selects a numeric field. Normalize CSV exports through a reproducible adapter, retain the original hash and transformation log, and review definitions. Do not create a fabricated JSON file just to satisfy this check. Source bytes and pointer agreement establish what a snapshot says, not authenticity, metric semantics, consent or attribution incrementality.

A derived figure instead has `calc: {op, inputs}`. `inputs` is an array of figure IDs. Supported operations:

- `ratio`: approved signatures are `roas = attributed_revenue / ad_spend`, `net_sales_mer = net_merchandise_sales / ad_spend`, `shopify_aov = purchase_merchandise_revenue_excluding_adjustments / orders`, `period_net_sales_per_order = net_merchandise_sales / orders`, `order_rate = orders / sessions`, `checkout_conversion = checkout_sessions / sessions`, and `contribution_break_even_roas = purchase_value_per_order / expected_contribution_before_ads_per_order`. The last denominator requires `cost_coverage: 1` and external review of all variable costs. Ratios need compatible windows and currencies. ROAS requires `account_scope` on both inputs and output, and an explicit matching `attribution` window on attributed revenue and output. Money ratios require the exact monetary unit, not just two equal unit labels. Contribution must be positive for a viable break-even target. Aggregate ROAS from summed value and spend after attribution reconciliation, never an unweighted mean of ratios.
- `sum`: only explicitly supported additive metrics: the monetary inputs/results of the commerce operations below, ad spend, attributed revenue, purchase merchandise revenue, orders, sessions, checkout sessions, units, clicks and impressions. Ratios, rates, per-order averages and unknown custom metrics fail; derive them from reconciled totals instead. Inputs require the same metric, unit, basis, currency and window, with distinct documented `partition` labels on the inputs. Attributed revenue also requires the same `attribution` definition and non-overlapping `order_ids`. Partition labels and order identifiers still need adapter verification. Platform-attributed revenue must not be renamed store revenue.

Three commerce operations verify signed component arithmetic without letting a formula silently omit a cost. Their `calc.inputs` must follow the exact metric order below; every figure uses `unit: "money"`, one currency and identical period. Declare `basis: "period_activity"` or `basis: "order_cohort"` on every component and output; the latter also requires the same `cohort_id`. Do not mix period-booked refunds with refunds on the current order cohort.

- `net_merchandise_sales`: `gross_merchandise_sales`, `merchandise_discounts`, `merchandise_refunds`. Signs are `+ - -`; inputs are nonnegative. Period activity can be negative during a prior-order refund wave. Cohort refunds cannot exceed that cohort's post-discount merchandise value.
- `contribution_before_ads`: `net_merchandise_sales`, `landed_cogs`, `restocked_cogs_credit`, `fulfilment_cost`, `payment_fees`, `return_handling_cost`, `shipping_revenue_ex_tax`, `other_variable_costs`. Signs are `+ - + - - - + -`. Shipping revenue is collected shipping less shipping refunds/tax, **before** any fulfilment expense; never subtract that expense twice. Output requires `cost_coverage: 1`; every cost field must exist, including sourced explicit zeros. Cost inputs declare non-overlapping `cost_buckets` arrays (for example product, shipping_out, pick_pack, payment_processing, return_handling); none can include advertising. The credit's `reverses` names its `landed_cogs` input. The output can validly be negative.
- `contribution_after_ads`: `contribution_before_ads`, `allocated_ad_spend`. Signs are `+ -`. Before/after outputs retain `cost_coverage: 1`. The ad input and output declare `allocation_method: "management_allocation"`; ad input includes an `allocation_note` explaining how spend is assigned to that period/cohort. This is a management allocation, not proven causal channel profit or full accounting net profit. Spend is nonnegative; after-ad contribution may be negative.

For illustrative figures, 10,000 gross merchandise sales - 1,000 discounts - 300 current-cohort refunds gives 8,700 net cohort sales. Deduct 3,500 COGS, add 120 restocked cost credit, deduct 700 fulfilment, 261 payment fees and 60 return handling, add 200 shipping revenue ex tax and deduct explicit zero other costs: contribution before ads is **4,499**. Allocating 3,000 advertising gives **1,499**. Those figures are unrelated to any real merchant. Source and cost-category review still matter: an arithmetic checker cannot prove an expense was classified truthfully.

Unknown operations, missing provenance, mixed currencies, source-value mismatches and cycles fail. FX conversion, cohort membership transformations and other accounting adjustments need a reviewed adapter producing a source snapshot; unsupported arithmetic must remain explicitly unverified, not silently cleared by a different metric label.

For supply/experiment arithmetic use `node tools/commerce-math.mjs input.json`, where the JSON is `{ "operation": "forecastInputCost", "inputs": { "currentCost": 100, "indexChange": 0.2, "passThrough": 0.25 } }` for an illustrative result of 105. Other exported operations are `safetyStock`, `materialInput`, `forecastUnits`, `stockPlan`, `replenishmentDay`, and `experimentReadout`; their explicit parameters and assumptions are in the tool. Save the input and result with the work. An inconclusive completed experiment is not proof of a small effect; inspect the interval against the practical threshold without extending until significant.
