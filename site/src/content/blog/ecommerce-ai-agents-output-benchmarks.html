Read the exact test conditions

Each role got one chosen ecommerce job, which ran twice, each time in a fresh gpt-6.1-sol session. One run used the role's locked specialist package, while the other used ordinary Sol as the plain model for comparison. Both runs had the same approved host tools and the same skills installed for everyone, and the shared task inputs within a pair were identical. The first set has 15 private store jobs and 65 made-up or public jobs, but many of the made-up jobs share records. So they are not independent businesses. Task inputs come from earlier development cases, but every output and every judgment was run fresh. Two separate fresh judges, gpt-6.1-sol and gpt-6.1-terra, inspected the real output files and evidence. Seed 32901880 balanced which run went first and how each one was labeled, and Terra saw the labels reversed. Clues inside a file can still reveal where it came from, so neutral labels do not guarantee the judges could not tell. No more than three ordinary jobs ran at once, while timed browser checks each ran alone. Fixes use fresh pairs on the same requests, and we record new package fingerprints. The original PR job received one declared extra input, which was verified company news, so that finished job is not a fix of the old unfinished case with unchanged inputs. No one in the test published anything, sent messages or changed a live account. Tools included with a subscription were allowed, but paid model APIs were not used. We record when each job started and when we saw it finish, but those times include waiting in line. So they do not measure speed. Input fingerprints identify the shared list of inputs, and we checked that the shared sources were intact in a separate private audit.

Our locked scoring guide grades five areas from zero to five: task completion (20%), evidence and math (25%), depth and usefulness (20%), brand and trade skill (20%), and usability and verification (15%). For the weighted total, each score is multiplied by its weight, and the results are added up and then divided by five. To pass, a job needs at least 80 out of 100 and at least four in every area. The requested real work must be complete, and it must clear every hard rule that applies. Hard rules cover made-up evidence or made-up work, key numbers and the groups they describe, who has permission, privacy, product facts and claims, and the real file that was requested. If we cannot tell whether a hard rule was met, the job does not pass. A job limited by missing tools still counts as unfinished. Which output a judge preferred is kept separate from whether the job was finished. We keep a record of raw failures, judge disagreements, and judge corrections that only fixed arithmetic. These diagnostic scores are our own method, and we do not claim that the evaluation advice we cite recommends weighted scoring.

Judge the work an ecommerce team would use

A useful agent leaves you with work you can inspect and use. For a media buyer, that might be an account audit with the source of each number, a reason to change the budget, and a test plan. For a copywriter, it might be several distinct ad concepts with product facts that support the claims. A page builder should leave a working page and explain how it checked the shopping flow.

That is the question behind these tests: did the agent finish the job in the brief, using the evidence it could access? A polished explanation is useful, but the work still needs to be correct. Each case names the expected output and the checks that matter for that role. It also states which parts could not be tested in the available setting.

The table covers a broad team because ecommerce work crosses departments. Ads depend on stock and margin. Product pages depend on product facts, customer concerns, and shipping terms. Support tickets can reveal a problem with a product or a confusing instruction. An agent that improves one number while ignoring these connections can make the business worse.

We therefore separate the quality of the output from the size of the promise. An audit can pass by finding a real problem, showing the evidence, and setting out a useful next action. It cannot claim to have increased sales until a live test measures that change. A tested code change can still deserve a recommendation to keep the old version when its costs outweigh its gains.

Give both versions the same job

A comparison needs a shared starting point. The specialist version receives its role package as well as the job brief and permitted source material. The plain model receives the same job and source access without that role package. This tests the added value of the instructions, relevant knowledge, tools, and checks shipped with the specialist.

Inputs are recorded before a run starts. File hashes help show whether a source changed between the two attempts. The record also names the model and the time of each run. An input that arrives later is a changed test condition, so it belongs in the repair record. It should never be presented as information that the first run already had.

The model doing the work does not receive the other version's answer. A judge reviews the finished outputs against the same brief. Independent reviews help expose differences in taste and interpretation, although they cannot remove every bias. The details of each test belong beside the scores so a reader can decide whether the comparison fits their own business.

One test per role provides useful examples, but a limited sample of work. A brand with thousands of products, several markets, or unusual checkout rules may need a different test set. These results are a development record. They are a starting point for choosing and checking an agent, rather than a prediction that every future job will receive the same score.

Several synthetic tasks share the same base business records. Testing many roles is not the same as testing many independent brands. New source sets, businesses and operators are still needed to test how well the methods transfer.

Make the right source available at the right step

More documents do not always make an answer better. A media buyer needs current account data, attribution rules, margins, offers, and the relevant channel playbook. A site speed specialist needs the frontend stack, affected templates, scripts, test conditions, and cart behavior. Sending both agents every document in the business adds noise and can hide the facts that decide the job.

The useful boundary is the question the agent must answer. Search should start with sources that fit the role and the task, then expand when the question crosses departments. A campaign plan may need stock data. A refund analysis may need the shipping policy. A source filter must make these links possible instead of trapping a specialist in its own folder.

Finding one relevant paragraph is only part of retrieval, the process of finding source material for an answer. Some questions need several pieces of evidence. A sales audit may need spend, attributed sales, store sales, refunds, and the dates and timezones behind each export. The final answer should make those dependencies visible. Missing evidence should lead to a narrower claim or a clear request for the missing input.

A source should carry enough context to judge whether it still applies. That includes its date, owner, scope, and any restrictions on its use. A brand's current policy should take priority over an old draft. A general playbook can suggest a method, but it cannot establish what happened in a particular account. Tests should check both successful retrieval and sensible behavior when the needed source is absent.

Keep the shared business context specific

The shared context is the briefing you would give a new colleague. It should describe the customers, products, markets, brand voice, visual rules, offers, and claims the business can support. Approved examples help an agent understand how those rules appear in real work. The file also needs an owner and a way to retire facts that are no longer true.

A color palette alone cannot make a creative on brand. The agent needs to know what the customer is trying to do, which product detail matters, and what the business is allowed to promise. For product visuals, the image must preserve the actual item's shape, material, and distinguishing details. A visually attractive result that changes the product is a failed commercial deliverable.

Voice examples are most useful when their purpose is explained. A product page, an email about a delayed order, and an offer ad can use different tones within the same brand. The context should show those differences. It should also separate approved copy from old experiments, competitor examples, and language that the company has rejected.

Access needs to follow the same boundaries as the company itself. An agency can share a general method across clients, but private client data must remain within that client's workspace. Agents should receive only the information needed for the task. A public case study needs a separate review because permission to use a document for work does not automatically mean permission to publish it.

Store decisions without turning guesses into facts

Different kinds of memory serve different jobs. Working memory holds the current brief, open questions, and progress on a task. Shared factual memory holds approved business information. A record of past tasks can preserve what was attempted, what happened, and why a decision was made. Skills and workflows describe repeatable ways to do the work.

Those records need different rules for updates. A temporary working assumption should not silently become a permanent brand fact. A successful past campaign is evidence about that campaign, not a universal rule for every offer. A failed experiment can still be useful if the record includes its conditions and the reason it failed. Memory is valuable when it helps the next agent make a better decision.

For a team of agents, handoffs should carry the evidence that affects the next step. A writer needs the approved claim, not a vague instruction to make the ad more persuasive. A developer needs the selected change, the acceptance checks, and the rollback plan. A reviewer needs the original brief as well as the final output. The receiving agent should be able to tell facts, assumptions, and decisions apart.

Reviewing past work can suggest improvements to the source structure or the workflow. Those suggestions should remain proposals until checked. Otherwise, a model can repeat its own error across future tasks. A short record with a source, date, and review status is often more useful than a large memory store whose contents nobody can trust.

Check calculations and execution separately from prose

Numbers need reproducible checks. Ratios should name their numerator and denominator. Totals should reconcile to the input rows. Currency, tax, refunds, attribution windows, and timezones can change the meaning of a result. A written explanation should make those choices clear enough for another person to reproduce the calculation.

When an agent builds something, the test should inspect what it built. A landing page needs browser checks on the relevant screen sizes. A shopping flow needs cart and checkout checks. A speed change needs repeated measurements under stated conditions, as well as checks that prices, images, variants, and customer sessions still behave correctly.

These checks answer different questions. A fast page can still have the wrong offer. A good-looking creative can still make an unsupported claim. A useful recommendation can still rely on incorrect arithmetic. The final decision should consider the hard failures before averaging softer judgments about clarity or style. A high overall score must not hide a broken requirement.

Keep raw measurements and failed checks. If the test setting fails, record that separately from the agent's output. If a real output fails, retain the result, explain the repair, and run the relevant test again. Changing a threshold after seeing a bad score would make the comparison much less useful.

Use automation to keep the business visible

Automating a symptom can hide its cause. Faster support replies may reduce a queue while confusing product instructions keep generating complaints. A good support workflow should preserve those patterns and surface them to the product team. The goal is to make recurring problems easier to see, even when the individual replies take less human time.

Some decisions depend on context that a system does not have. A supplier relationship, a sensitive customer history, or the feel of a physical product may change the right answer. The workflow should identify where that context matters and let the owner supply it. Review should focus on the decisions with meaningful consequences and unclear rules.

People also need to retain the skills needed to judge the work. For important recommendations, a brief explanation of the evidence and alternatives helps the owner stay involved. Occasional independent checks can reveal whether the team still understands the calculation, campaign decision, or technical change well enough to recover when the system fails.

Relationship work deserves its own place in the process. An agent can prepare a supplier update or summarize customer concerns, while a person handles a conversation that builds trust. Time saved through automation can support those conversations. A workflow should make that choice explicit instead of assuming every interaction is a task to remove.

The engineering ideas behind the tests

Stanford CS329Z: Engineering AI Agents treats an agent as a system of models, retrieval, tools, data and evaluation. Its course covers how to choose components and assess their tradeoffs. That supports a practical question in this study: which parts of a specialist package help it finish a specific ecommerce job? The course is a design resource, not a certification of these agents.

Hamel Husain and Shreya Shankar's AI Evals FAQ puts attention on error analysis, clear pass/fail decisions, and alignment with human reviewers. The Standard Agent Specification emphasizes domain focus, explicit models, portable agents and composition. Those ideas inform narrow roles and clear handoffs. Taking inspiration from the specification does not establish runtime conformance. These tests assess the packages and models named in the record, under their stated host conditions.

  • Private store evidence uses the dates, definitions and attribution windows that were recorded with it. An attribution window is the time span in which a sale is credited to an ad. Those snapshots do not show how the accounts perform today, and raw store records, photos and financial figures stay private.
  • A real file or a local browser check does not prove a live connection to Shopify, advertising, payments, email or SMS. Each case lists the provider, rights and production checks it is still missing.
  • AI judges make mistakes. They have not been calibrated against a panel of experienced human ecommerce operators. We keep their disagreements, and we keep arithmetic corrections separate from real changes in judgment.
  • Because each side ran once and each targeted fix ran once, the test cannot show that results repeat or that one side is statistically better. It also cannot show lower cost, higher real sales, or better work than a human designer. The plain model is ordinary Sol with host tools, not Claude Code.
  • We make no claim about token cost or total speed. Jobs ran at the same time, some browser launches failed, and jobs waited in line, so the finish times are unsuitable for that purpose.
  • Local speed samples depend on the machine they ran on. Made-up PHP-WASM and SQLite tests do not show how fast real PHP and MySQL sites run, and lab measurements are not the same as Core Web Vitals from real visitors.
  • Public excerpts and chosen real files can be traced back to actual finished outputs. A fingerprint alone cannot verify what is in a hidden source file, and private test files mean the public cannot fully repeat the test.
  • Fixing these agents can improve them, but it also makes this data less useful for predicting how they behave on new jobs. Earlier failures and plain-model wins remain part of the result.
  • Some evidence links work in the original run folder but break in the copied judge folders. Even so, the judges received the shared sources separately. This copying problem can influence what judges say about usability and which output they prefer. We keep the original judgments, because a broken link in a copied folder does not by itself mean the agent created a bad source link.
  • One independent review of sourcing stalled and never wrote a judgment. We kept the unfinished session and the steps we took to recover, and then a fresh Terra session received the same locked task. No written verdict was discarded or replaced, so this was a retry of the review, not another fix of an agent's output.
  • In one product ad design pair, the coordinator clarified a permission the owner had already given. It allowed local editing that combines images while keeping the product photos unchanged. Both sides received identical permission text, but the plain model got it during its work while the specialist got it at the start. The locked inputs and scoring rules did not change, and we disclose this timing difference while making no claim about speed.
  • The video fix changed what the host could do. A free, fixed-version offline speech-to-text tool became available to both fresh runs before they started. It supports an AI review of a machine transcript for meaning, but it does not mean a human listened, that sound and picture line up exactly, or that the full video was watched. Because this condition changed, we cannot credit the retry result solely to the specialist package.

These are development evaluations on selected ecommerce jobs. They do not establish a population-wide success rate, measured sales growth, or superiority over a human specialist. Model judgments have their own errors. Repeated tests on new businesses and review by experienced operators remain necessary.

Questions about the agent benchmarks

Does a pass mean the agent changed a live business?

Read the execution limits on each case. A test can assess an actual file, calculation, or local storefront change while leaving a live store untouched. Publishing an ad, sending customer messages, and changing a budget require their own access and approval.

Why can the plain model win when the specialist passes?

Pass status checks whether an output meets the brief. Preference compares two acceptable outputs. The plain model may write a clearer answer, find stronger evidence, or make a simpler recommendation. We publish those outcomes alongside the specialist wins.

Are these 80 new outputs or old scores carried forward?

Every case in this report has fresh completed runs and new judgments. Earlier reports remain separate. This report includes the original PR task, and the case record identifies that task explicitly.

Can I reproduce the result exactly?

The public file records the models, times, file hashes, conditions, and excerpts. Some private fixtures cannot be shared. Model outputs also vary between runs. Use the method with your own approved inputs, then keep every result so the next comparison has a clear basis.
