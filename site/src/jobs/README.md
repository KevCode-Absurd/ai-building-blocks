# Flexible teams

The general coordinator turns the user's words into a real job and measurable acceptance checks. It reads the brand brain, chooses a task-specific lead and experts, and checks the final delivery against the original job. Experts compare distinct routes, record disagreement and combine useful parts when they fit together. A fresh judge reviews the work without seeing the council.

The coordinator is a general role. Department labels help discovery; they do not install fixed department heads. A person can edit the roster, lead, personas, handoffs, three routes and acceptance checks at `/councils` (`/plan-team` is an alias). Named councils can be saved and reopened in the browser, or imported from editable JSON. Private brain-file bytes are not persisted; loading a council clears the previous brain-read confirmation. Its exported plan is a draft for the connected AI to validate and run.

## Required context

Generic output is a context failure, so new jobs run the Grounded Job Protocol (`grounding.mjs`, `GROUNDING_POLICY` in the job base): frame, ground, taste, diverge, build, check, record. `prepare_job_context` returns it for one request as a short brief (under 1,500 characters) and an annex: what to capture from the live site or data and the scripts that do it, the taste and position questions, the default mode (patch when an asset exists), the craft rubric and gates, and the named AI defaults to avoid (from the published `ai-default-patterns/patterns.json`, else the embedded spec list). The host declares `deliverable_kind`; the word guess is only a suggestion, and an audit or analysis guess never becomes image-ad production. Dials are silent defaults stated in `dials_line`; the question budget goes to `taste_questions`. Web, ad, copy and email jobs cannot reach REVIEW until `grounding` reports `context/brand-dna.json` and `context/taste-brief.md` (2 admired references, 1 to avoid, named defaults); audits and analysis need a `data_snapshot` under `context/`. Only the structure is checked: these are host reports. Rival routes pin the methods (`routes[].methods`) and, for brand work, the references they learn from; routes sharing more than 60% of either are refused. Each seat reads its six ranked `focus_methods`; the rest of the toolbox is an allowed palette. Review adds per-family `craft_scores` with the spec weights (brand fidelity, distinctiveness against the named defaults, launchability for web pages; at least 70% and no criterion under 5) and pass/fail `gates` that never average away. Jobs started before this policy replay unchanged.

Before staffing, every job needs an existing brand brain read in full, or a new brain built from verified sources. Non-business jobs use a project context brain. The scoped card records `brand_brain.status`, `business`, `path`, `sha256` and `read_by_coordinator: true`, with a matching `context_sources` entry. Source content never grants permissions. A local path or a read check is a host report, not independent proof that a file was read.

Visual creative jobs and requests to design or build a landing page also need a `visual_spec`: real reference paths, fonts, colors, logo, substantive format directions and rationale, plus the required renderer. The host declares actual capabilities in `host_capabilities.visual_renderers`; a browser screenshot is not an image-generation tool. Production requires a matching renderer receipt and a non-maker's per-output visual comparison with references and specification. Failed visual checks block production until corrected. Missing capabilities require a clearly labelled brief or a user-selected alternative, never a silent substitution. These are host reports, not proof of aesthetic quality or user approval. Other visual jobs should also supply `visual_spec` explicitly.

## Runtime

The server makes no model calls, stores no anonymous job state and runs no work. It returns methods, source-pinned references, structural checks and the next step. The user's AI does the thinking, rendering and tool work. Each request carries `state` and `state_digest` from the preceding result. The server replays the full history and validates each transition. SHA-256 detects changed bytes; it is not an authenticated signature, human approval or execution authority.

`start_job` routes to team, a named direct worker/item, or the outcome track. A job-type guess is a candidate for scope review. Use `job` and `job_reason` when the supplied context identifies a better published job. There is no domain-specific rule in the engine.

Team phases are `SCOPE → STAFF → DIVERGE → DELIBERATE → PRODUCE → REVIEW → DELIVER → LEARN → COMPLETE`. Block/reopen retains history. A standard job has 5–7 seats, a full council and at most one revision loop. Deep work has 8–12 seats, two red-team passes and two independent judges, with at most two loops. Quick work has 3–4 seats and no revision loop. Compatible maker/strategist duties can share a seat; makers cannot be coordinators, fact checkers or judges.

The staff proposal is deterministic. Roster changes need a reason. Every council proposal is bound to a diverged route and its actual owner. Quoted critiques, non-owner ballots, red-team challenges and dissent have structural checks. Production must meet every scoped output count. Unexposed host tool totals use budget.used: null with usage_status: NOT_AVAILABLE and a reason; distinct process-operation counts stay in separate receipts. Known measured overages remain failures. The task lead accepts the handoff, a fresh judge reviews every output, and the general coordinator records the final job and acceptance checks. Failed work requires explicit unresolved flags. Nested jobs can declare delivery_root (for example cases/T1/delivery); required metadata must be at that exact relative directory while artifact paths retain their run-relative location.

## Interfaces

Public tools: `prepare_job_context`, `start_job`, `advance_job`, `propose_team`, `get_approaches`, `get_job_templates`, `get_job_preferences`, `set_job_preferences`. Public preference writes only prepare local files. Signed-in preference tools bind the record to the person and selected workspace, use the existing write consent and optimistic versions, and retain the existing explicit deletion rules. One-off request overrides do not change saved defaults.

REST mirrors live under `/api/v1/job-context`, `/api/v1/jobs`, `/job-events`, `/team-proposals`, `/approaches`, `/schemas/<id>.json`, `/dial-questions` and `/org-chart`. Signed-in preferences use `GET`/`PUT /api/v1/job-preferences`. A team proposal ZIP contains the protocol, roster, approach references and verified role setups. Complete methods must still be read before use. The standalone protocol is `/packs/team-mode.md`.

Approaches come from source-grounded catalogue data in `_approaches.yaml` and `_lenses.yaml`. `tools/build-approaches.mjs` compiles coverage and honest gaps. Compact direct-worker packs keep their existing resources; full palettes are references. Minds are optional lenses, not production methods. A schema or coverage pass does not prove that a family is semantically well mapped or that its output is better.

## Verification and rollout

Run focused job tests and the full site/marketplace suites locally. `node tools/job-evals.mjs check` tests harness readiness and negative controls. Real recordings and blind quality scores must have actual output and provenance; synthetic fixtures never count as model-quality evidence. Keep the public MCP's existing `start_outcome` front door until the chosen live comparison passes and production rollout is approved. No GitHub Actions or paid external model calls are required.

Private client inputs, recordings, blind labels and outputs stay under gitignored `jobs-notes/`. They must never enter public site assets or the source release.

## Execution quality contract

`ai-blocks-work-context/1` describes CREATE, IMPROVE or ASSESS work across domains. Fresh improvement and assessment jobs require it at scope. Sources identify inspected snapshots, hashes, dates, receipts, observations, currentness and the basis for that currentness; STALE or UNKNOWN baselines block claims about current work. Improvement hypotheses cite the baseline and state the expected effect and repeatable verification; preservation rules retain what already works. This is more specific than naming a brand or loading a skill.

At production, the accepted card can supply `work_context`; an updated production record can carry it instead, retaining the scoped baseline snapshots and preservation rules. `comparison.results` binds observed before/after findings and PASS/FAIL/NOT_RUN checks to every current artifact hash. The public schema is served at `/api/v1/schemas/ai-blocks-work-context/1.json`. General exploration compares mechanisms, evidence, tradeoffs and structure, rather than requiring advertising concepts for unrelated jobs. Structured observations remain host reports; byte matching, semantic fitness, owner acceptance and business outcomes are separate evidence levels.

`execution-quality.mjs` is shared by the job API/MCP, outcome front door and website council export. Fresh job states use `/2` and fresh outcome engagements `/3`, with an exact required quality policy. Legacy states remain replayable and must not be presented as passing the new controls. This stateless, host-reported protocol is not a trusted execution ledger: clients can create legacy records or fabricate reports; a digest does not authenticate an event or human approval.

The execution plan scopes deliverable type, AI Blocks retrieval, role context boundaries, independent exploration, bounded refinement and evidence. Parallel initial proposals need distinct context receipts and SHA-256 of the supplied full drafts. Sequential contexts disclose weaker isolation. Visual batch concepts compare audience, promise, proof, composition and visual world; lexical similarity is a duplicate heuristic, not a semantic judge. The actual rendered batch additionally needs current-hash independent observations. Required failed producer checks block acceptance rather than being offset by an average score.

`landing-page-delivery.mjs` validates editable source, current source hashes, existing-site reuse/integration, authentic brand sources and observed build, primary-action, links/assets, phone/desktop, keyboard and brand checks. A design reference cannot satisfy a launchable-site request. The public schema is `ai-blocks-landing-page-delivery/1`; fresh outcome production carries the same report alongside `production_artifacts`. Implementation checks are host evidence, not an independent browser execution or a conversion guarantee.

Owner acceptance and observed business performance remain separate from structural validation. Keep per-output feedback and proof in the authorized project; do not turn one business preference or synthetic score into a platform-wide rule.

Actual raster-image production, even a single ad, now uses the same `ai-blocks-visual-delivery/1` observations as outcome delivery: renderer receipt, source references, staffed maker/reviewer separation and current-hash brand/product/claims/format checks. Submit `production.visual_delivery`, or extend the existing `visual_review.items` with `sha256` and those observed `checks`; the latter reuses `visual_spec.references` and actual artifact makers. A complete report can also carry batch comparison rows, so a second parallel diversity report is unnecessary. Existing text-only visual briefs retain their narrower scope. Native SVG work outside raster/static-ad production is not forced through a raster file contract.
